# i-dolly-backend

[English](README.md) | 日本語

**アルバム／シングルのマーケットプレイス** を備えたアイドル公演の **チケット予約** バックエンドです。
スキーマ設計、レイヤードな API アーキテクチャ、マイグレーションの規律、RBAC といったバックエンドの
エンジニアリングを示すための **ポートフォリオプロジェクト** として構築しました。汎用的な FastAPI の EC サイトから
出発し、段階的にアイドルチケットのドメインへと作り変えてきました — アイドル／グループ、会場／公演、
抽選方式のチケット販売、そして元のカート／注文／決済の仕組みの上に載せたアルバム／グッズのマーケットプレイスです。

これは **本番システムではありません**。未完成の部分は以下のドキュメントで明記しています —
[既知の制限事項](#既知の制限事項) を参照してください。

## ドメイン

- **Identity（認証・権限）** — ロールベースのアクセス制御（`admin` / `manager` / `fan`）、事務所単位にスコープされたマネージャー。
- **Talent（タレント）** — 事務所、アイドルグループ、アイドル、メンバーカラー、ポジション。
- **Events & ticketing（イベント・チケット）** — 会場、公演、券種（抽選または一般販売）、抽選の希望／キャンペーン／応募、
  発券済みチケット。券種は **座席指定ではなくキャパシティベース** です — これは手抜きではなく意図的なスコープ判断です
  （`database-design_JP.md` の冒頭を参照）。
- **Marketplace（マーケットプレイス）** — アルバム／シングル／EP の詳細、グッズの詳細（ペンライトやその他の公式グッズ）、
  ジャンルで拡張した商品／カテゴリ — 元のカート／注文／決済／配送の仕組みを再利用しています。
- **Shared（共通）** — アプリ内通知、お問い合わせフォーム（inquiries）、FAQ の即時回答。

## 技術スタック

- **FastAPI**（Python 3.12）+ リクエスト／レスポンススキーマに **Pydantic v2**
- **PostgreSQL**（**SQLAlchemy 2.0** ORM 経由）、マイグレーションに **Alembic**（一本の直線的なチェーン）
- キャッシュ（msgpack でシリアライズ）とレート制限に **Redis**
- **Celery** ワーカー（Redis をブローカー／リザルトバックエンドに使用）— マネージャーが実行する抽選と、すべての
  トランザクションメール送信をバックグラウンドジョブとして実行。本番では Render の Background Worker
- **JWT** 認証 — 短命なアクセストークン + ローテーションするリフレッシュトークン、httponly Cookie
- ローカル開発用の **モック決済ゲートウェイ**、加えて **PayPal** 連携（チケット購入でサンドボックス検証済み）—
  まだ検証できていない部分は [既知の制限事項](#既知の制限事項) を参照
- トランザクションメールに **Resend**
- お問い合わせページの FAQ 即時回答に **Claude API**（`anthropic` SDK、Haiku 4.5）—
  任意機能で、`ANTHROPIC_API_KEY` が未設定なら無効
- アイドル／商品画像のためのローカルディスク／S3 互換オブジェクトストレージの抽象化
- ローカル開発に **Docker Compose**、CI に **GitHub Actions** — `lint` ジョブ（`ruff check .`）と、
  それとは別の `test` ジョブ（Postgres + Redis サービス、Alembic マイグレーション、pytest + カバレッジ）

詳細と判断の理由: [`docs/architecture_JP.md`](docs/architecture_JP.md) §1。

## 実際に完成しているもの

- **すべてのテーブルで UUID 主キー** — 連番の整数 ID を使わないため、`/products/search/2`、`/products/search/3` のように
  推測してリソースを列挙されることがない
- Identity／RBAC、事務所単位にスコープされたマネージャー
- グループ、アイドル、メンバーカラー、ポジション、会場、公演、券種、抽選の希望／キャンペーン／応募、チケット、
  アルバム詳細、ジャンル、グッズ詳細の完全な CRUD（ORM + スキーマ + サービス + ルーター）
- アイドルと商品のローカル／S3 画像アップロード
- お金と公平性に関わる不変条件を強制する 12 個のデータベーストリガー（ファンのみ購入可能、転売防止の上限、
  公演のチケットキャパシティ、抽選の応募上限など）
- **マネージャーが実行する抽選**（`PUT /concerts/lottery-draw/{id}`）— ランクカスケード方式の抽選アルゴリズムを
  Celery ワーカーで非同期に実行し、行レベルロックにより同じ公演に対する 2 回の実行で二重抽選されることを防ぐ
- **アプリ内通知**（注文／チケット／抽選の確認、抽選結果、パスワードリセットなど）— ポーリング型のフィード
  （`GET /notifications/mine`、`/unread-count`）で、WebSocket／SSE レイヤーは意図的に持たない
- Celery タスクから Resend 経由で送信する **トランザクションメール**（メール認証、パスワードリセット、
  注文／チケット／抽選当選後の支払い確認、お問い合わせの受付通知）。抽選の当落結果は設計上アプリ内通知のみ
- 抽選フローと並ぶ **一般販売チケットの購入**（`POST /tickets/checkout`）。一般販売キャンペーンの期間で制御
- **お問い合わせフォーム**（`POST /inquiries/submit`、ゲストも利用可）と AI による **FAQ 即時回答**
  （`POST /inquiries/instant-answer`、英語と日本語に対応）。厳選した FAQ ファイルの内容だけから回答し、
  答えられない場合はフォームにフォールバックする
- モックゲートウェイに加え、実際の（サンドボックス）決済処理のための **PayPal 決済**
- 両方の購入エンドポイントに冪等性キーを付与し、リトライやダブルクリックされたリクエストで二重課金が起きないようにしている
- グループとアイドルはハードな `DELETE` ではなく論理削除（無効化／再有効化）
- アイドル、グループ、会場、公演、マーケットプレイス商品の架空のフルラインナップを投入する、冪等なシードスクリプト
  （`scripts/seed.py`）

詳細な最新の状況 — ETL／分析パイプライン、スタッフ向けのお問い合わせ閲覧画面、検証済みの PayPal の決済拒否／Webhook の
経路など、*まだ* 完成していないものも含めて: [`docs/project_status_JP.md`](docs/project_status_JP.md) §2 と §5。

## 既知の制限事項
- レート制限は、ルートごとの場当たり的な判断ではなく明示的なティアポリシー（`docs/architecture_JP.md` §3）によって
  全 26 個のルーターファイルをカバーするようになった — ただし、そのポリシー自体（どのルートがどのティアに属するか、
  その正確な上限値と時間枠）はポートフォリオの範囲での判断であり、正式な負荷試験に基づいたものではない。

- 既知の未解決バグ（プロキシ背後で IP ベースのレート制限が偽装可能、Redis 障害時の処理がない、PayPal の保留状態の
  クリーンアップなど）は `docs/bugs_JP.md` で管理しており、修正計画は `docs/plans/` にある。

重要度順に並べた完全な一覧 — すでに修正済みのもの（購入時の競合状態、レートリミッターのキー衝突、Webhook の冪等性など）
も含む: `docs/project_status_JP.md` §4 と `docs/bugs_JP.md`。

## はじめに（Docker）

### 前提条件
- Docker + Docker Compose

### 1. クローンと設定
```bash
git clone https://github.com/TranXuanAnh930/i-dolly-backend.git
cd i-dolly-backend
cp .env.example .env
```
`.env` を埋めてください — 最低限 JWT シークレット、そしてメールのフローをエンドツーエンドで動かしたい場合は
Resend のキーが必要です（有効なキーがなくてもアプリはローカルで動作しますが、メール送信は行われません）。
モック決済ゲートウェイにはサードパーティのキーは不要です。PayPal Sandbox アプリのクライアント ID／シークレットは、
代わりに実際の PayPal 決済の経路を試したい場合にのみ必要です。

### 2. スタックの起動
```bash
docker compose up --build
```
FastAPI アプリ、PostgreSQL、Redis、Celery ワーカーが起動し、起動時に `alembic upgrade head` が実行されます。
実行された抽選（`PUT /concerts/lottery-draw/{id}`）を実際に処理するのはワーカーです — ワーカーがないと、
エンドポイントは "scheduled" を返しますが抽選は実行されません。

### 3. API を試す
```
http://localhost:8000/docs
```

### 4. （任意）サンプルデータの投入
```bash
docker compose exec app python scripts/seed.py
```
事務所、アイドルグループ、会場、公演、券種、マーケットプレイス商品といった架空のフルラインナップを投入します。
冪等なので、再実行しても安全です。

同じデータの日本語版（名前、説明文、公演タイトル、商品タイトル）が必要な場合は、代わりに `scripts/seed_ja.py` を
実行してください。データベースごとにどちらか一方だけを使ってください — 両者はユーザーのメールアドレスを共有しており、
どちらのバージョンのデータがすでに存在していてもスキップします。

### 5. テストの実行
```bash
docker compose exec app pytest --cov=app
```

### 6. Lint の実行
```bash
pip install -r requirements-dev.txt
ruff check .
```
コンテナの外で実行します（DB／Redis は不要）— `requirements-dev.txt` は通常の依存関係に加えて `ruff` を
インストールします。CI がすべての push／PR で実行するのと同じコマンドです。

### 7. スタックの停止
```bash
docker compose stop
```
データベースのデータは保持されます。
