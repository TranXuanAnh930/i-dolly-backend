# フロントエンドのタスク: アカウントごとの制限のメッセージと、未払いの注文の「発送」ボタン

[English](auth-limits-and-unpaid-orders.md) | 日本語

**バックエンドの変更:** `docs/bugs_JP.md` #7（マージ・デプロイ済み、リリース 1.4.2）、および #26 と #14
（ブランチ `fix/ship-unpaid-and-cancel-route`）。
**種類:** 破壊的変更ではない。フロントエンドはこれらに対応しなくても動き続ける。各タスクは、汎用的なメッセージや
誤解を招くボタンを正しいものに置き換えるだけなので、バックエンドの後にリリースしてよい。
**参照:** リクエストとレスポンスの正確な形は `docs/api-spec_JP.md` にある。このファイルには、何が変わったかと、
フロントエンドがそれに対して何をすべきかだけを書く。以下のファイル名は `i-dolly-frontend` のもの。

## 1. バックエンドで変わったこと

### 1a. ログインとパスワード再設定の依頼に、メールアドレスごとの制限が付いた（#7）

既存の IP ごとの制限に加えて、2 つのルートがメールアドレスごとにも数えるようになった:

| エンドポイント | 制限 | 制限を超えたとき |
|---|---|---|
| `POST /account/login` | メールアドレスごとに 15 分あたり 5 回の**失敗**まで。ログインに成功するとカウントはリセットされる | `429`、コード `too_many_login_attempts` |
| `POST /profile/forgot-password` | メールアドレスごとに 1 時間あたり 3 回まで | `429`、コード `too_many_reset_requests` |

- あるメールアドレスがログインの制限を超えている間は、そのアドレスでの**すべての**ログインが 429 になる。正しい
  パスワードでも同じ。15 分の期間が終わると自動的に解除される。
- どちらの制限も、未登録のメールアドレスを同じように数えるので、レスポンスからアカウントの有無は分からない。
  アカウントが存在するかのような文言にしないこと。
- IP ごとの 429（コード `rate_limited`、`detail` は「…try again after N seconds」）と違い、この 2 つの `detail` には
  **秒数が含まれない**。`ApiError.retryAfter` は `null` になる。

### 1b. 発送には支払い済みの注文が必要（#26）

| エンドポイント | 変更前 | 変更後 |
|---|---|---|
| `PATCH /order/{order_id}/ship` | 発送ステータスが `pending`/`processing` の注文なら何でも発送した | 注文の `status` が `"confirmed"` であることも必須。そうでなければ `400`、コード `order_not_paid` |
| `PATCH /order/update_shipping_status/{order_id}`（管理者） | 任意のステータスを設定できた | `confirmed` でない注文では `400 order_not_paid`。ただし新しいステータスが `"cancelled"` の場合は除く |

なぜ重要か: PayPal の注文は、決済がキャプチャされる前の購入時点で、発送ステータスが `pending` になる。そのため、
放置された PayPal の購入は、注文の `status: "pending"` と、発送できそうに見える発送ステータスを持って、マネージャーの
注文ページに表示される。`GET /order/manager-orders-page` は変わっておらず、各注文の `status` をすでに返している。

### 1c. `PATCH /order/cancel/{order_id}` はなくなった（#14）

このルートは登録されなくなり、`404` を返す。現在フロントエンドにこれを呼ぶ箇所はない
（`src/services/store/order.service.js` にキャンセルのメソッドはない）ので、削除するものはない。これに対する
「注文をキャンセル」ボタンを追加しないこと: バックエンドが返金と在庫の戻しを実装するまで、注文のキャンセルは
サポートされない。

## 2. フロントエンドのタスク

### タスク 1: 新しい 2 つの 429 のコードを翻訳する

現在はどちらのコードにも翻訳がないので、`ApiError.message`（`src/services/apiError.js`）は
`errors.rate_limited_generic` にフォールバックする:「試行回数が多すぎます。しばらく待ってからもう一度お試しください」
に相当するメッセージ。安全ではあるが曖昧で、「しばらく」は最大 15 分や 1 時間になりうる。

- `src/i18n/locales/en.js` と `ja.js` に `errors.too_many_login_attempts` と `errors.too_many_reset_requests` を
  追加する。文言の案:
  - `too_many_login_attempts`:「このメールアドレスでのログインの失敗が多すぎます。15 分後にもう一度試すか、
    パスワードを再設定してください。」
  - `too_many_reset_requests`:「このメールアドレスでの再設定の依頼が多すぎます。1 時間後にもう一度お試しください。
    すでに送信されたリンクが届いていないか、受信トレイもご確認ください。」
- `apiError.js` の変更は不要: キーが存在すれば、`message` がそれを使う。

### タスク 2: `too_many_login_attempts` のときのログインページの動作

`src/pages/auth/Login.vue` は、`rate_limited` を特別扱いし（カウントダウン、送信のブロック）、`invalid_credentials` も
特別扱いする（入力欄が赤くなる）。

- `too_many_login_attempts` はどちらでもない: カウントダウンは出さず（数える秒数がない）、入力欄も赤くしない。
  パスワードは正しいかもしれないため。
- 翻訳したメッセージを表示し、その横にパスワード再設定ページへのリンクを置く。
- ファンがメールアドレスを編集したらエラーを消す動作はそのままにする: 別のメールアドレスには別のカウントがある。

`src/pages/auth/ForgotPasswordPage.vue` はすでに `error.message` を表示しているので、タスク 1 だけで足りる。

### タスク 3: 支払い済みの注文にだけ「発送」を表示する

`src/pages/manager/ManagerOrdersPage.vue` で:

- `canShip(order)` は発送ステータスしか確認していない。`order.status === 'confirmed'` を追加する。
- 両方のロケールファイルに `errors.order_not_paid` を追加する。古いデータからボタンが表示されていた場合（例:
  ステータスが変わる前に一覧を読み込んでいた）のため。文言の案:「この注文は支払いが完了していないため、発送
  できません。」
- 任意: 一覧で未払いの注文を見分けやすくする。`order.status` からのステータスバッジはすでに表示されている。
  「発送」ボタンのない `pending` の注文は、未払いまたは放置された PayPal の購入であり、マネージャーの対応を待って
  いるものではない。

`PATCH /order/update_shipping_status` を使う管理者画面がある場合は、同じルールを適用する: `confirmed` でない注文には
`cancelled` だけを選べるようにする。

## 3. 受け入れチェックリスト

両方の変更を含むバックエンドに対して実行する。未払いの注文の確認には PayPal のサンドボックスが必要。使えない場合は、
データベースで注文の `status` を直接 `pending` にする。

- [ ] **ログイン:** 1 つのメールアドレスでパスワードを 5 回間違え、6 回目を試すと、汎用のメッセージではなく新しい
      ログインのメッセージが、英語と日本語の両方で表示される。
- [ ] **ログイン:** その状態で入力欄は赤くならず、カウントダウンもなく、パスワード再設定へのリンクが見える。
- [ ] **ログイン:** そのメールアドレスの正しいパスワードも、期間が終わるまでは同じメッセージで拒否される。
- [ ] **ログイン:** 同じブラウザから、別のメールアドレスではログインできる。
- [ ] **ログイン:** IP ごとの制限（別々のメールアドレスで素早く 11 回試す）では、これまでどおりカウントダウンが
      表示される。
- [ ] **パスワード再設定の依頼:** 1 つのメールアドレスで 1 時間以内に 4 回目の依頼をすると、新しい再設定の
      メッセージが表示される。
- [ ] **マネージャーの注文:** 発送ステータスが `pending` または `processing` の `confirmed` の注文には「発送」が
      表示され、これまでどおり発送できる。
- [ ] **マネージャーの注文:** `status: "pending"` の注文（PayPal での購入を始めたが承認していない）には「発送」
      ボタンが表示されない。
- [ ] **マネージャーの注文:** `cancelled` の注文には「発送」ボタンが表示されない。
- [ ] **マネージャーの注文:** 未払いの注文に対して呼び出しを強行すると（例: 古いタブから）、`order_not_paid` の
      メッセージがトーストで表示され、行は変わらない。
- [ ] 「注文をキャンセル」を出している画面がない。

## 4. スコープ外

- IP ごとの制限とそのカウントダウンは変わっていない。
- 放置された PayPal の注文は、引き続き永久に `pending` のまま残り、ファンの注文履歴とマネージャーの注文ページに
  表示される（`docs/bugs_JP.md` #27）。それらを隠したり期限切れにしたりするのは、後のバックエンドの変更で行う。
  クライアント側で除外しないこと。
- ファンによる注文のキャンセル（`docs/bugs_JP.md` #14）は実装されていない。
