# フロントエンドのタスク: マネージャー設定ページと住所の取得で認証情報を送る

[English](manager-pages-and-address-auth.md) | 日本語

**バックエンドのブランチ:** `refactor/add-test-coverage`（`docs/bugs_JP.md` #28 と #29 を修正）。
**種類:** 破壊的変更。このバックエンドがデプロイされると、トークンなしでこれらのエンドポイントを呼んでいるページは
動かなくなる。フロントエンドの変更を先に、またはバックエンドと同時にリリースすること。
**参照:** 正確なリクエストとレスポンスの形は `docs/api-spec_JP.md` にある。このファイルは、何が変わったか、そして
フロントエンドがそれに対して何をすべきかだけを挙げる。

## 1. バックエンドで変わったこと

### 1a. 6 つのマネージャー設定ページがログイン必須になり、事務所でスコープされるようになった

| エンドポイント | 変更前 | 変更後 |
|---|---|---|
| `GET /products/manager-products-page` | 公開。`?company_id=` で求められたものを何でも返していた | 🔒 マネージャー／管理者。マネージャーは常に自分の事務所のものを取得 |
| `GET /products/manager-product-form-page` | 公開。同上 | 🔒 マネージャー／管理者。自分の事務所の商品 **と** アイドル／グループの選択肢 |
| `GET /idols/manager-idols-page` | 公開。すべての事務所のアイドル | 🔒 マネージャー／管理者。マネージャーは自分の事務所のものを取得 |
| `GET /idols/manager-idol-form-page` | 公開。すべての事務所のアイドル／グループ | 🔒 マネージャー／管理者。マネージャーは自分の事務所のものを取得 |
| `GET /groups/manager-groups-page` | 公開。すべての事務所のグループ | 🔒 マネージャー／管理者。マネージャーは自分の事務所のものを取得 |
| `GET /concerts/manager-events-page` | 公開。すべての事務所の公演 | 🔒 マネージャー／管理者。マネージャーは自分の事務所の公演を取得 |

レスポンスの形（フィールド名と型）は **変わっていない**。変わったのは、誰がエンドポイントを呼べるかと、どの行が
返ってくるかである:

- **マネージャー:** 自分の事務所の行だけ。商品ページでは、これまでどおり所有者のない商品（アルバム／グッズの詳細が
  ないもの）も含む。マネージャーが送った `company_id` クエリパラメータは **無視される**。
- **管理者:** これまでどおり、すべての事務所の行。2 つの商品ページでは、管理者は引き続き `?company_id=` を渡して
  1 つの事務所に絞り込むことも、省略してすべてを取得することもできる。
- **共有の参照データはフィルタされないまま:** `venues`（イベントページ）、`colors`（アイドルフォームと商品フォーム）、
  `categories`（商品フォーム）。
- **新しいエラー:** 有効なトークンがなければ `401`、ファンのアカウントには `403`、ユーザーごと・エンドポイントごとに
  1 分あたり 30 リクエストを超えると `429`。

### 1b. `GET /shipping_addresses/fetch_byid/{address_id}` がログイン必須になった

- 以前はすべての呼び出しで `500` を返していたので、住所編集フォームの初期値の読み込みは、このバックエンドに対して
  一度も動いたことがない。
- 現在はファンのアクセストークンが必要で、呼び出したユーザー自身の住所だけを返す。それ以外の ID は、他のユーザーの
  ものも含めて `404` を返す。
- `PUT /shipping_addresses/update/{id}` と `DELETE /shipping_addresses/delete/{id}` はすでにトークンが必須だった。
  これらも、他のユーザーの住所に対しては `404` を返すようになった。以前は成功してしまっており、それがセキュリティ上の
  バグだった。

## 2. フロントエンドのタスク

### タスク 1: 6 つのマネージャーページの呼び出しでアクセストークンを送る

- マネージャー／管理者の設定画面がこれらのエンドポイントを取得しているすべての箇所で、
  `GET /order/manager-orders-page` やマネージャーの書き込み系エンドポイントの呼び出しがすでにしているのと同じ方法で、
  `Authorization: Bearer <access_token>` を付ける。共通の認証済み API クライアントやインターセプターがあれば、素の
  `fetch` ではなくそれを経由させる。
- `401` の場合は、既存のリフレッシュフロー（`credentials: "include"` 付きの `POST /account/refresh`）を通して 1 回
  再試行し、それでもだめならユーザーをログインに送る。
- `403` の場合、ユーザーはログインしているがマネージャーでも管理者でもない。マネージャー領域から別の場所へ
  リダイレクトする。これらの画面にファンがたどり着けること自体あってはならないので、ルートガードを確認すること。
- ユーザーがログインする前に、これらのページをプリフェッチしたり温めたりしないこと。例えばアプリ起動時や公開
  レイアウトで。そうした呼び出しは今後 `401` を返す。

**影響を受ける画面**（`api-spec_JP.md` §1 より）: マネージャーの商品テーブルと商品の作成／編集フォーム、マネージャーの
アイドルテーブルとアイドルの作成／編集フォーム、マネージャーのグループテーブル、マネージャーの公演テーブルと公演の
作成フォーム。

### タスク 2: マネージャー向けのクライアント側の事務所フィルタリングを削除する

- フィルタリングはサーバーが行うようになったので、これらのレスポンスをログイン中のマネージャーの `company_id` で
  フィルタしているコードは、マネージャーのロールについては削除できる。残しておいても、フィルタ済みのデータに対しては
  何もしないので害はない。削除は後片付けであり、正しさのために必須ではない。
- **管理者** のフォームが、フォームで選んだ事務所に選択肢を絞り込むために使っているクライアント側のフィルタリングは
  **残す**。例えば、アイドルフォームのグループの選択肢は、選択された `company_id` で `groups` をフィルタしている。
  管理者は引き続きすべての事務所の行を受け取る。
- 2 つの商品ページについて、マネージャーの画面から `?company_id=` を送るのをやめる。今は無視される。管理者の画面は、
  管理者が事務所を選んだときには引き続き送る。

### タスク 3: 住所編集フォームの初期値の読み込み

- ファンのアクセストークンを付けて `GET /shipping_addresses/fetch_byid/{address_id}` を呼ぶ。
- `404` は「住所が見つからない」として扱う: 例えば、住所の一覧に戻って再読み込みする。
- 壊れたエンドポイントを回避するために、フォームが別の方法（例えば `GET /shipping_addresses/fetch` が返す一覧から
  初期値を入れる）を使っていた場合は、その回避策を残しても、`fetch_byid` に切り替えてもよい。今はどちらも動く。

### タスク 4: レート制限の扱い

これらのページは現在 **ユーザーごと・エンドポイントごとに 1 分あたり 30 リクエスト** に制限されている。通常の画面遷移
ならそれをはるかに下回るが、ポーリングしたり、レンダリングのループで再取得したりしている画面がないか確認すること。
`429` の場合、`detail` のメッセージに何秒待てばよいかが書かれている。すぐに再試行せず、間隔をあけること。

## 3. 受け入れチェックリスト

このブランチからビルドしたバックエンドに対して、ファン 1 人、管理者 1 人、異なる事務所（A と B）のマネージャー 2 人で
実行する:

- [ ] **マネージャー A:** 商品、アイドル、グループ、公演の設定ページが読み込まれ、事務所 A の行（商品ページでは
      所有者のない商品も）だけが表示される。
- [ ] **マネージャー A:** 商品作成フォームのアイドルとグループの選択肢には、事務所 A のアイドルとグループだけが並ぶ。
      カテゴリとカラーの選択肢は変わらない。
- [ ] **マネージャー A:** アイドル作成フォームのグループの選択肢には、事務所 A のグループだけが並ぶ。
- [ ] **マネージャー A:** 公演作成フォームの会場の選択肢には、引き続きすべての会場が並ぶ。
- [ ] **管理者:** すべての設定ページですべての事務所が表示され、商品の画面で事務所を選ぶとこれまでどおり一覧が
      絞り込まれる。
- [ ] **ファン:** マネージャーの URL を直接開くと別の場所へリダイレクトされ、マネージャーのデータは表示されない。
- [ ] **ログアウト状態:** マネージャーの URL を開くとログインに移動し、`401` のレスポンスから何もレンダリングされない。
- [ ] **期限切れのアクセストークン:** マネージャーのページが、目に見えるエラーなしにリフレッシュフローで回復する。
- [ ] **ファン:** 「住所を編集」で `fetch_byid` から正しく初期値が入る。
- [ ] **ファン:** 自分のものではない住所 ID（例えば URL を書き換えたもの）では「見つかりません」と表示され、その保存や
      削除は拒否される。
- [ ] 公開ページで、これらのエンドポイントへのコンソールエラーや予期しないネットワーク呼び出しがない。

## 4. スコープ外

- `GET /management_companies/all` は設計上 **公開** のまま。選択肢用に事務所名を返す。
- 公開ページ（`/products/store-page`、`/idols/members-page`、`/groups/groups-page`、`/concerts/events-page`、
  `*/detail` の各ページ）は変わっていない。
