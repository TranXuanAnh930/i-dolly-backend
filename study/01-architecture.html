Topic 01

Layered architecture & errorsレイヤードアーキテクチャとエラー処理

How a request travels through router, service and model, and how a failure deep inside becomes a clean JSON error.

リクエストがルーター・サービス・モデルをどう通るか、そして奥で起きた失敗がどうやってきれいな JSON エラーになるか。

TL;DRSay this in 30 seconds30秒で言えること

  • Three layers per feature: router (HTTP only), service (business logic + ORM queries), model/schema (SQLAlchemy tables + Pydantic shapes).機能ごとに3層：ルーター（HTTP だけ）、サービス（業務ロジックと ORM クエリ）、モデル/スキーマ（SQLAlchemy のテーブルと Pydantic の型）。
  • Code is grouped by domain (identity, talent, events, marketplace, shared), not by technical type alone.コードは技術的な種類だけでなくドメイン（identity・talent・events・marketplace・shared）ごとにまとめる。
  • Services raise typed exceptions that carry an HTTP status and a stable error code. The router maps them once.サービスは HTTP ステータスと固定のエラー code を持つ型付き例外を投げる。ルーターは1か所で変換する。
  • Every error body has the same shape: {"detail", "code"}. Unexpected crashes become a JSON 500 that still has CORS headers.すべてのエラーは同じ形 {"detail", "code"}。予期しない例外も CORS ヘッダー付きの JSON 500 になる。
  • Handlers are plain def, because everything below them is synchronous.ハンドラーは普通の def。下の層がすべて同期処理だから。

PRIMERThe theory you need必要な理論

Why layers at allそもそもなぜ層に分けるのか

Separation of concerns: each layer changes for a different reason. HTTP details (status codes, headers, auth dependencies) change independently of business rules (stock, lottery windows), which change independently of storage (tables, indexes). Keeping them apart means you can test business rules without HTTP, and swap one layer without rewriting the others.

関心の分離：各層は別々の理由で変更される。HTTP の詳細（ステータス、ヘッダー、認証）、業務ルール（在庫、抽選期間）、保存方法（テーブル、インデックス）はそれぞれ独立して変わる。分けておけば HTTP なしで業務ルールをテストでき、1つの層を入れ替えても他を書き直さずに済む。

Dependency injection in FastAPIFastAPI の依存性注入

Depends(...) lets a route declare what it needs (a DB session, the current user, a rate-limit check). FastAPI builds those values per request, and a yield dependency runs cleanup after the response. Tests can override any dependency with app.dependency_overrides.

Depends(...) でルートが必要なもの（DB セッション、現在のユーザー、レート制限）を宣言する。FastAPI はリクエストごとにそれを作り、yield を使う依存関係はレスポンス後に後片付けをする。テストでは app.dependency_overrides で差し替えられる。

def vs. async defdef と async def

HandlerハンドラーWhere FastAPI runs it実行される場所Blocking call inside中でブロッキング処理をすると
async defOn the event loopイベントループ上Freezes every request in the processプロセス内の全リクエストが止まる

SQLAlchemy sessions, bcrypt, httpx.post to PayPal and boto3 are all blocking. So plain def is the correct choice here, not the lazy one.

SQLAlchemy のセッション、bcrypt、PayPal への httpx.post、boto3 はすべてブロッキング。だからここでは普通の def が「手抜き」ではなく正しい選択。

IN THE REPOWhere i-dolly does iti-dolly での実装箇所

1. The folder layout1. フォルダ構成

app/
  router/<domain>/<feature>.py            # HTTP: Depends, one service call, map errors
  services/<domain>/<feature>_service.py  # business rules + ORM queries
  db/models/<domain>/<feature>.py         # SQLAlchemy tables
  schema/<domain>/<feature>.py            # Pydantic Create / Read / Update
  exception/  deps/  cache/  tasks/  utils/  # cross-cutting pieces

Domains: identity, talent, events, marketplace, and shared for cross-domain features like notifications. Response schemas are always separate classes from ORM models, so a new DB column never leaks into the API by accident.

ドメイン：identity・talent・events・marketplace、通知などドメインをまたぐ機能は shared。レスポンス用スキーマは ORM モデルと必ず別クラスなので、DB に列を足しても API に勝手に漏れない。

2. One request, three layers2. 1つのリクエストと3つの層

# router: HTTP only
@router.put("/update/{id}", response_model=GroupRead)
def update_existing_group(id: uuid.UUID, data: GroupUpdate,
        current_user: Users = Depends(require_manager_or_admin), db: Session = Depends(get_db)) -> Group:
    try:
        result = GroupService.update_group(db, id, data, current_user)
    except ServiceError as e:
        raise HTTPException(status_code=e.status_code, detail=str(e)) from e

# service: rules + queries, no FastAPI imports
db_group = db.get(Group, id)
if not db_group:
    raise NotFoundError("Group not found")
if GroupService._manager_scope_violation(current_user, db_group.company_id):
    raise ForbiddenError("Managers can only manage groups for their own company")

Services are classes of @staticmethods used as namespaces (GroupService.update_group(db, …)). They are never instantiated, and the session is passed in on every call.

サービスは @staticmethod を並べたクラスで、名前空間として使う（GroupService.update_group(db, …)）。インスタンス化はせず、セッションは毎回引数で渡す。

3. The exception hierarchy3. 例外の階層

CodedError                  # has a stable `code` for clients
├── ServiceError (400)      # app/exception/common.py
│   ├── NotFoundError (404)
│   ├── ForbiddenError (403)
│   ├── BadRequestError (400)
│   └── ConflictError (409)
├── CartItemError ...       # app/exception/checkout.py (multi-step checkout)
└── TriggerViolationError   # app/exception/db_triggers.py (Postgres rules)

4. One error shape for the whole API4. API 全体で1つのエラー形式

def error_code(exc: StarletteHTTPException) -> str:
    if isinstance(exc, ApiHTTPException):
        return exc.code
    if isinstance(exc.__cause__, CodedError):   # set by `raise ... from e`
        return exc.__cause__.code
    return STATUS_CODES.get(exc.status_code, f"http_{exc.status_code}")

This is why from e matters: the handler reads the original service error through __cause__ to get its code. Drop from e and the client gets the generic bad_request instead of, say, entries_closed.

from e が重要な理由：ハンドラーは __cause__ から元のサービス例外を読み、その code を取り出す。from e を忘れると、例えば entries_closed ではなく汎用の bad_request が返ってしまう。

5. Middleware order and the CORS trap5. ミドルウェアの順番と CORS の罠

register_exception_handlers(app)
# Added before CORSMiddleware so CORS wraps it and unexpected 500s still carry CORS headers.
app.add_middleware(UnhandledErrorMiddleware)
app.add_middleware(CORSMiddleware, ...)

·

Starlette wraps middleware in reverse order of adding, so the one added last is the outermost. FastAPI's default 500 is built outside all middleware, which means no CORS headers, and the browser shows a confusing "network error". Catching the crash inside the CORS layer fixes that.

Starlette では後から追加したミドルウェアほど外側になる。FastAPI 標準の 500 はすべてのミドルウェアの外で作られるので CORS ヘッダーがなく、ブラウザには分かりにくい「ネットワークエラー」と表示される。CORS 層の内側で例外を捕まえることで解決している。

6. Session per request6. リクエストごとのセッション

def get_db() -> Generator[Session, None, None]:
    db = session()
    try:
        yield db
    finally:
        db.close()

7. Strategy pattern: storage7. Strategy パターン：ストレージ

StorageBackend is an abstract class with LocalStorageBackend and S3StorageBackend. get_storage() picks one from settings, so callers never know which one they got ().

StorageBackend は抽象クラスで、LocalStorageBackend と S3StorageBackend がある。get_storage() が設定から選ぶので、呼び出し側はどちらを使っているか意識しない（）。

8. A circular-import trap8. 循環 import の罠

Models import Base from app.db.base_class, never from app.db.base. base.py imports every model so Alembic can see them all. A model importing base.py would import itself in a loop ().

モデルは Base を app.db.base_class から import し、app.db.base からは決して import しない。base.py は Alembic のために全モデルを import しているので、モデルがそれを import すると循環する（）。

WHYWhy this design, and what it costsこの設計を選んだ理由とそのコスト

  • Exceptions over return codes: an earlier version returned strings like "forbidden" and every router translated them. Exceptions can't be ignored by accident, carry a specific message, and stop the flow at the exact failing check.戻り値ではなく例外：以前は "forbidden" のような文字列を返し、各ルーターで変換していた。例外なら見落とせず、具体的なメッセージを持ち、失敗した確認の位置で処理を止められる。
  • Stable code field: the frontend branches on code, not on English text, so wording (or a Japanese translation) can change without breaking clients.固定の code：フロントエンドは英文ではなく code で分岐するので、文言や日本語訳を変えてもクライアントは壊れない。
  • Static-method services: simple and explicit, with no DI container. The cost is that tests must patch full import paths instead of injecting a fake service.static メソッドのサービス：DI コンテナがなく単純で明示的。代わりにテストでは偽のサービスを注入できず、完全な import パスで patch する必要がある。

WEAK SPOTSKnown gaps you should own自分から説明すべき既知の問題

Boilerplate定型コード

Every router repeats try / except ServiceError / raise HTTPException from e, and checkout routers stack several except blocks in a careful order (). Since each error already carries its status, one global app.add_exception_handler(CodedError, …) could replace most of it.

各ルーターで try / except ServiceError / raise HTTPException from e を繰り返しており、チェックアウト系は複数の except を慎重な順番で並べている（）。例外が自分のステータスを持っているので、グローバルな app.add_exception_handler(CodedError, …) 1つでほぼ置き換えられる。

Services commit themselvesサービスが自分でコミットする

Most service methods call db.commit() internally. That's simple, but two service calls can't share one transaction. The checkout flow works around this by having PaymentService only flush, and letting the outer service commit once. A Unit of Work pattern would make this explicit.

多くのサービスメソッドは内部で db.commit() を呼ぶ。単純だが、2つのサービス呼び出しで1つのトランザクションを共有できない。チェックアウトでは PaymentService は flush だけにして、外側のサービスが1回だけコミットすることで回避している。Unit of Work パターンを使えば明示的にできる。

QUESTIONSPractice questions練習問題

BASICWalk me through the structure of your backend.バックエンドの構成を説明してください。

Three layers per feature, grouped by domain. Routers handle HTTP: dependencies for the session, the user and rate limits, one service call, and error mapping. Services hold business rules and all ORM queries. Models are SQLAlchemy tables, and Pydantic schemas define request and response shapes. Cross-cutting code (auth dependencies, cache, exceptions, background tasks) lives in its own packages.

機能ごとに3層で、ドメイン単位にまとめている。ルーターは HTTP を担当し、セッション・ユーザー・レート制限を依存関係で受け取り、サービスを1回呼んでエラーを変換する。サービスは業務ルールとすべての ORM クエリを持つ。モデルは SQLAlchemy のテーブル、Pydantic スキーマがリクエストとレスポンスの形を決める。認証、キャッシュ、例外、バックグラウンドタスクなどの横断的なコードは別パッケージにある。

BASICWhy not return the ORM model directly from an endpoint?エンドポイントから ORM モデルをそのまま返さないのはなぜ？

The API contract should not change when the table changes. A separate Read schema controls exactly which fields go out, so a new column like a password hash can't leak. It also gives OpenAPI docs and validation for free.

テーブルが変わっても API の契約は変わるべきではない。Read スキーマを分ければ返すフィールドを正確に決められ、パスワードハッシュのような新しい列が漏れない。OpenAPI ドキュメントと検証も自動で得られる。

MIDYour handlers are all def. Isn't async faster?ハンドラーがすべて def ですが、async の方が速くないですか？

Only if the work underneath is async. Here the DB driver, bcrypt, the PayPal client and boto3 are all blocking. In an async def handler they'd run on the event loop and freeze every other request. As plain def, FastAPI runs them in a threadpool, so they really run concurrently. To go async I'd need an async driver like asyncpg and async SQLAlchemy all the way down.

下の処理が非同期である場合だけ。ここでは DB ドライバー、bcrypt、PayPal クライアント、boto3 がすべてブロッキング。async def の中で使うとイベントループ上で動き、他の全リクエストが止まる。普通の def なら FastAPI がスレッドプールで実行するので本当に並行に動く。非同期にするなら asyncpg と非同期 SQLAlchemy を全層で使う必要がある。

MIDHow does a ForbiddenError in a service reach the client?サービスの ForbiddenError はどうやってクライアントに届きますか？

The service raises it with a message. The router catches ServiceError and raises HTTPException(403, …) from e. The global handler builds {"detail": message, "code": "forbidden"}, taking the code from __cause__. A raise site can also override the code, for example code="entries_closed".

サービスがメッセージ付きで投げる。ルーターが ServiceError を捕まえ HTTPException(403, …) from e を投げる。グローバルハンドラーが __cause__ から code を取り、{"detail": メッセージ, "code": "forbidden"} を作る。投げる側で code="entries_closed" のように code を上書きすることもできる。

MIDWhy do you need a custom middleware for 500 errors?500 エラー用に独自ミドルウェアが必要なのはなぜ？

FastAPI's built-in 500 response is generated outside the middleware stack, so it has no CORS headers. The browser then blocks it and the frontend sees a generic network error with no body. The custom middleware sits inside CORS, logs the traceback, and returns a JSON 500 with code: "internal_error" that the browser can read.

FastAPI 標準の 500 はミドルウェアの外側で作られるので CORS ヘッダーがない。ブラウザがそれをブロックし、フロントエンドには本文のない一般的なネットワークエラーとしか見えない。独自ミドルウェアは CORS の内側にあり、トレースバックをログに出して、ブラウザが読める code: "internal_error" 付きの JSON 500 を返す。

SENIORWhat would you change in this architecture as the team grows?チームが大きくなったら、このアーキテクチャの何を変えますか？

(1) One global handler for CodedError to remove per-router try/except. (2) A Unit of Work so services flush and one place commits, which makes cross-service transactions explicit. (3) Injected service instances or repositories, so tests can swap fakes without patching import paths. (4) A domain_events outbox, already planned, so side effects like emails and cache busting happen reliably after commit. I'd keep the domain folders, because they map well to future service boundaries.

(1) CodedError 用のグローバルハンドラーを1つ作り、ルーターごとの try/except をなくす。(2) Unit of Work を導入し、サービスは flush だけ、コミットは1か所にしてサービス間のトランザクションを明示する。(3) サービスやリポジトリをインスタンスとして注入し、import パスを patch せずに偽物に差し替えられるようにする。(4) すでに計画にある domain_events のアウトボックスで、メール送信やキャッシュ削除などの副作用をコミット後に確実に実行する。ドメインごとのフォルダは、将来のサービス分割の境界にそのまま使えるので残す。
