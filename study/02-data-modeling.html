Topic 02

Data modeling & schema designデータモデリングとスキーマ設計

How 31 tables model idols, concerts, lotteries and a marketplace, and which layer enforces each rule.

31個のテーブルでアイドル・公演・抽選・マーケットをどうモデル化し、各ルールをどの層で強制しているか。

TL;DRSay this in 30 seconds30秒で言えること

  • Four domains: identity, talent, events & ticketing, marketplace, plus shared tables like notifications.4つのドメイン：identity・talent・events とチケット・marketplace、加えて通知などの共有テーブル。
  • Every primary key is a UUID, so ids can't be guessed or enumerated.主キーはすべて UUID。id を推測したり順番に列挙したりできない。
  • Ticket tiers are capacity-based (VIP has N seats), not a seat map. One row per tier per sale method.チケット枠は座席表ではなく定員ベース（VIP は N 席）。枠×販売方法ごとに1行。
  • Product kind lives in exactly one place, categories. Kind-specific facts go in 1:1 detail tables (album_details, merch_details).商品の種類は categories の1か所だけで管理。種類ごとの情報は 1対1の詳細テーブル（album_details・merch_details）に置く。
  • Rules are layered: types and NOT NULL → CHECK / UNIQUE → triggers for money and fairness rules → service checks for everything else.ルールは層で守る：型と NOT NULL → CHECK / UNIQUE → お金と公平性に関わるルールはトリガー → それ以外はサービス層。

PRIMERThe theory you need必要な理論

Normalization in one breath正規化をひとことで

Store each fact once. If two columns say the same thing, they will eventually disagree. 1NF: no repeating groups. 2NF/3NF: every non-key column depends on the key, the whole key, and nothing but the key. You denormalize on purpose, for speed, and then you own keeping the copies in sync.

1つの事実は1か所にだけ保存する。同じことを表す列が2つあれば、いつか食い違う。第1正規形：繰り返しグループを持たない。第2・第3正規形：キー以外の列はキー全体にだけ依存する。非正規化は速度のために意図的に行い、その場合はコピーを同期させる責任を負う。

Three ways to model subtypesサブタイプをモデル化する3つの方法

Where to enforce a ruleルールをどこで強制するか

The database protects data from every writer (APIs, scripts, future bugs), but its errors are harder to turn into good messages. The service layer gives good messages but only protects the paths that call it. Strong designs check in the service for UX and let the DB be the final guarantee for rules that must never break.

データベースはすべての書き込み元（API、スクリプト、将来のバグ）からデータを守るが、そのエラーを分かりやすいメッセージにするのは難しい。サービス層は良いメッセージを返せるが、そこを通る経路しか守れない。良い設計では、UX のためにサービス層で確認し、絶対に破ってはいけないルールは DB を最後の保証にする。

2. Capacity-based ticket tiers2. 定員ベースのチケット枠

class TicketType(Base):
    concert_id     = Column(UUID, ForeignKey("concerts.id", ...), nullable=False)
    tier           = Column(Enum(TicketTier, name="ticket_tier_enum"), nullable=False)
    price          = Column(Numeric(10, 2), nullable=False)
    total_quantity = Column(Integer, nullable=False)
    sold_quantity  = Column(Integer, nullable=False, server_default="0")
    sale_method    = Column(Enum(SaleMethod, name="sale_method_enum"), ...)
    __table_args__ = (
        UniqueConstraint("concert_id", "tier", "sale_method"),
        CheckConstraint("sold_quantity <= total_quantity"),
    )

A seat map would need venue → section → row → seat tables and per-seat locking. Capacity tiers keep it to one counter row per tier and still support pricing, lottery and checkout. The CHECK is a last line of defense against overselling, and a trigger makes sure all tiers together don't exceed the concert's capacity (a CHECK can't look at sibling rows).

座席表にすると 会場 → セクション → 列 → 座席 のテーブルと座席ごとのロックが必要になる。定員ベースなら枠ごとにカウンター1行で済み、価格・抽選・購入にも対応できる。CHECK は売り越しに対する最後の防御で、全枠の合計が公演の定員を超えないことはトリガーで保証する（CHECK は兄弟行を参照できない）。

3. One fact, one place: categories + detail tables3. 1つの事実は1か所に：カテゴリーと詳細テーブル

class Category(Base):
    name             = Column(String, nullable=False, unique=True)   # Album | Single | EP | Merch
    is_resale_capped = Column(Boolean, nullable=False, server_default=func.true())

class AlbumDetail(Base):
    product_id = Column(UUID, ForeignKey("products.id", ...), primary_key=True)  # 1:1
    idol_id, group_id = ...
    __table_args__ = (CheckConstraint("idol_id IS NOT NULL OR group_id IS NOT NULL"), ...)

· ·

Using the product's id as the detail table's primary key is what makes it 1:1. An older release_type column (album/single/EP) was dropped because it said the same thing as the category. A trigger stops a product from having both an album row and a merch row. The resale cap reads the is_resale_capped flag, so exempting a category is a data change, not a code change.

商品の id を詳細テーブルの主キーにすることで1対1になる。以前の release_type 列（album/single/EP）はカテゴリーと同じ事実を表していたので削除した。トリガーで、1つの商品がアルバム行とグッズ行の両方を持つことを防ぐ。転売上限は is_resale_capped フラグを読むので、あるカテゴリーを対象外にするのはコード変更ではなくデータ変更で済む。

The team's rule for triggers: only when the failure costs money or fairness (an admin buying a ticket, a scalper buying 40 albums). Ordinary consistency stays in the service layer.

トリガーを使う基準：失敗するとお金や公平性が損なわれる場合だけ（管理者がチケットを買う、転売屋がアルバムを40枚買うなど）。普通の整合性チェックはサービス層に置く。

5. Small details worth mentioning5. 話す価値のある細かい工夫

  • Generated column: venues.size (small / medium / large / stadium) is computed by Postgres from total_capacity, so it can never be stale ().生成列：venues.size（small / medium / large / stadium）は Postgres が total_capacity から計算するので、古くなることがない（）。
  • Soft delete: idols and groups have is_active, so a deactivated idol keeps their album and concert history ().論理削除：アイドルとグループは is_active を持ち、無効化しても過去のアルバムや公演の履歴が残る（）。
  • Tenant key: company_id on company-owned rows, plus on manager users (). Topic 05 covers how it's enforced.テナントキー：会社が所有する行と、マネージャーのユーザーに company_id がある（）。強制方法はトピック05。
  • Python enums wired to DB enums: an invalid status fails as a 422 at the API boundary instead of an IntegrityError deep in a commit.Python の enum と DB の enum を連携：不正なステータスはコミットの奥の IntegrityError ではなく、API の入口で 422 になる。

WHYWhy this design, and what it costsこの設計を選んだ理由とそのコスト

  • UUID keys: sequential ids let anyone walk /orders/1, /orders/2… to scrape or probe. The cost is 16-byte keys and random inserts that spread across the B-tree index. UUIDv7 (time-ordered) would keep the privacy and fix most of the index locality.UUID キー：連番 id だと誰でも /orders/1, /orders/2… と辿ってデータを集めたり探ったりできる。コストは16バイトのキーと、B-tree インデックス全体に散らばるランダムな挿入。UUIDv7（時刻順）ならプライバシーを保ったまま局所性の問題をほぼ解決できる。
  • Class-table subtypes: albums need track_count and genres, merch needs an edition and a color. Separate tables let each have real CHECK constraints instead of a wide table full of NULLs.クラステーブルでのサブタイプ：アルバムには track_count とジャンル、グッズにはエディションと色が必要。テーブルを分ければ、NULL だらけの広いテーブルではなく、それぞれに本物の CHECK 制約を付けられる。
  • Counters instead of rows for stock: sold_quantity is a denormalized count of tickets. It makes the stock check one locked row instead of a COUNT(*), at the cost of keeping it in sync inside the same transaction.在庫は行数ではなくカウンター：sold_quantity はチケット数を非正規化したもの。在庫確認が COUNT(*) ではなくロックした1行で済む代わりに、同じトランザクション内で同期させる必要がある。

WEAK SPOTSKnown gaps you should own自分から説明すべき既知の問題

Money as float金額が float

Ticket prices are Numeric(10, 2), but products.price, orders.total_price and orders_items.price are Float (, ). Floats can't represent 0.1 exactly, so totals can drift by fractions of a unit. Fix: Numeric columns and Decimal in Python, via a migration. docs/bugs.md lists this as a code smell.

チケット価格は Numeric(10, 2) だが、products.price・orders.total_price・orders_items.price は Float（、）。float は 0.1 を正確に表せないため、合計がわずかにずれうる。対策：マイグレーションで Numeric 列にし、Python では Decimal を使う。docs/bugs.md でもコードの問題点として挙げられている。

bugs.md #2

Deleting a product deletes order history. orders_items.product_id is ON DELETE CASCADE () and product delete is a hard delete. Fix: ON DELETE RESTRICT plus a soft delete for products, like idols already have.

商品を削除すると注文履歴も消える。orders_items.product_id が ON DELETE CASCADE で（）、商品削除は物理削除。対策：ON DELETE RESTRICT にし、アイドルと同様に商品にも論理削除を入れる。

CHECKLISTI can explain…説明できること

QUESTIONSPractice questions練習問題

BASICWhy did you use UUIDs instead of auto-increment ids?自動採番ではなく UUID を使ったのはなぜ？

Sequential ids are guessable. Anyone can iterate over /orders/1, 2, 3… to scrape data or probe for another user's cart or ticket. UUIDs make that impractical and also let the app generate ids before inserting. The trade-off is larger keys and random index inserts. UUIDv7 would reduce the index cost.

連番 id は推測できる。誰でも /orders/1, 2, 3… と順に試してデータを集めたり、他人のカートやチケットを探ったりできる。UUID ならそれが現実的でなくなり、挿入前にアプリ側で id を作ることもできる。代わりにキーが大きく、インデックスへの挿入がランダムになる。UUIDv7 ならインデックスのコストを減らせる。

BASICWhat's the difference between a CHECK constraint and a trigger?CHECK 制約とトリガーの違いは？

A CHECK can only look at the row being written, like sold_quantity <= total_quantity. A trigger runs a function that can query other rows and tables, like summing all tiers of a concert against its capacity. CHECKs are cheaper and declarative. Use a trigger only when the rule needs other rows.

CHECK は書き込み中の行しか見られない（例：sold_quantity <= total_quantity）。トリガーは他の行やテーブルを検索できる関数を実行する（例：公演の全枠の合計を定員と比べる）。CHECK の方が軽く宣言的。他の行が必要なルールにだけトリガーを使う。

MIDHow do you model albums and merch in the same product catalog?アルバムとグッズを同じ商品カタログでどうモデル化していますか？

A shared products table holds price, stock and image, so cart and checkout work for everything. categories says what kind it is. Kind-specific data goes in 1:1 tables keyed by product_id: album_details (tracks, format, genres) and merch_details (edition, color). A trigger stops one product from being both. It's class-table inheritance.

共通の products テーブルに価格・在庫・画像を置き、カートと購入はすべての商品で同じように動く。種類は categories が表す。種類ごとの情報は product_id をキーにした1対1のテーブルに置く：album_details（曲数、形式、ジャンル）と merch_details（エディション、色）。トリガーで両方を持つことを防ぐ。いわゆるクラステーブル継承。

MIDWhy not use a seat map for concert tickets?コンサートのチケットに座席表を使わないのはなぜ？

Scope. Idol lotteries sell by tier, and the seat is often assigned later. A seat map means a venue → section → row → seat hierarchy, one row per seat, and locking individual seats. Capacity tiers need one counter per tier and still support pricing, the lottery and checkout. It was a deliberate decision, recorded in the design doc.

スコープの問題。アイドルの抽選は枠単位で販売し、座席は後で決まることが多い。座席表にすると 会場 → セクション → 列 → 座席 の階層、座席ごとの行、座席単位のロックが必要になる。定員ベースなら枠ごとにカウンター1つで済み、価格・抽選・購入にも対応できる。設計ドキュメントに記録された意図的な判断。

MIDWhere do you enforce business rules: the app or the database?業務ルールはアプリと DB のどちらで強制しますか？

Both, by severity. Every rule is checked in the service for a clear error. Rules whose failure costs money or fairness (fans only, one ticket per concert, the resale cap) also get a trigger, because they must hold even against a future endpoint or a manual SQL fix. Ordinary consistency stays in the service to keep the schema simple.

重要度に応じて両方。すべてのルールはサービス層で確認して分かりやすいエラーを返す。失敗するとお金や公平性が損なわれるルール（ファンのみ購入可、1公演1枚、転売上限）は、将来のエンドポイントや手動の SQL 修正に対しても守られるよう、トリガーでも強制する。普通の整合性はスキーマを単純に保つためサービス層に置く。

SENIORWhat would you change in this schema before going to production?本番に出す前に、このスキーマの何を変えますか？

(1) Money to Numeric everywhere. (2) orders_items.product_id to RESTRICT plus a soft delete for products, and a snapshot of name and price on each order line, so history survives catalog edits. (3) UUIDv7 for index locality. (4) Review indexes against real query plans; for example, the draw filters entries by campaign and status, so a composite index on (campaign_id, status) could help. (5) Drop the deprecated is_admin column now that role is the source of truth.

(1) 金額をすべて Numeric にする。(2) orders_items.product_id を RESTRICT にして商品に論理削除を入れ、各注文明細に名前と価格のスナップショットを保存して、カタログを編集しても履歴が残るようにする。(3) インデックスの局所性のために UUIDv7 にする。(4) 実際のクエリプランでインデックスを見直す。例えば抽選は応募をキャンペーンとステータスで絞るので、(campaign_id, status) の複合インデックスが効くかもしれない。(5) role が正となった今、非推奨の is_admin 列を削除する。
