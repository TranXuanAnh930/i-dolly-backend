Topic 03

Migrations with AlembicAlembic によるマイグレーション

How 64 migrations change a live schema safely: ordering, backfills, enums, and what can't be undone.

64個のマイグレーションで稼働中のスキーマを安全に変える方法：順番、バックフィル、enum、元に戻せない変更。

TL;DRSay this in 30 seconds30秒で言えること

  • Every schema change is an Alembic migration in one linear chain. Never create_all().スキーマ変更はすべて一直線の Alembic マイグレーション。create_all() は使わない。
  • One concern per migration, ordered by foreign-key dependency.1マイグレーションに1つの関心事、外部キーの依存順に並べる。
  • Tightening a column is backfill first, then constrain, so existing rows never violate the new rule.列を厳しくするときは先にバックフィル、次に制約。既存の行が新しいルールに違反しないようにする。
  • Enum types are created with an idempotent DO $$ … EXCEPTION WHEN duplicate_object block, so a half-applied deploy can't crash-loop.enum 型は冪等な DO $$ … EXCEPTION WHEN duplicate_object ブロックで作る。途中で失敗したデプロイでも再起動ループにならない。
  • CI runs alembic upgrade head on an empty Postgres 16 on every push, before the tests.CI はプッシュのたびに、テストの前に空の Postgres 16 で alembic upgrade head を実行する。

PRIMERThe theory you need必要な理論

What a migration tool gives youマイグレーションツールが提供するもの

A versioned, ordered list of schema changes stored in git. The database records which version it's on (Alembic's alembic_version table), so every environment can be brought to the same state with one command, and every change is reviewed like code.

git に保存された、バージョン付きで順番のあるスキーマ変更の一覧。DB は自分が今どのバージョンかを記録する（Alembic の alembic_version テーブル）。そのため1つのコマンドですべての環境を同じ状態にでき、変更はコードと同じようにレビューされる。

Expand → migrate → contract拡張 → 移行 → 縮小

The safe pattern for changing live data: (1) expand: add the new column as nullable; (2) migrate: backfill old rows and deploy code that writes both; (3) contract: add NOT NULL or drop the old column once nothing reads it. Each step is backward compatible with the code running at the time.

稼働中のデータを変える安全なパターン：(1) 拡張：新しい列を NULL 可で追加、(2) 移行：古い行をバックフィルし、両方に書くコードをデプロイ、(3) 縮小：誰も古い列を読まなくなってから NOT NULL を付ける、または古い列を削除する。各ステップはその時点で動いているコードと後方互換がある。

Postgres DDL is transactionalPostgres の DDL はトランザクション対応

Unlike MySQL, Postgres can roll back CREATE TABLE or ALTER TABLE if a later step fails, so a migration either fully applies or not at all. Exceptions: CREATE INDEX CONCURRENTLY and some enum operations can't run inside a transaction.

MySQL と違い、Postgres は後のステップが失敗したら CREATE TABLE や ALTER TABLE もロールバックできる。そのためマイグレーションは全部適用されるか、まったく適用されないかのどちらか。例外：CREATE INDEX CONCURRENTLY や一部の enum 操作はトランザクション内で実行できない。

2. Idempotent enum creation2. 冪等な enum の作成

op.execute(sa.text("""
    DO $$ BEGIN
        CREATE TYPE campaign_status_enum AS ENUM ('open', 'drawn', 'completed', 'cancelled');
    EXCEPTION
        WHEN duplicate_object THEN NULL;
    END $$;
"""))

This replaced Enum.create(bind, checkfirst=True) after a real incident: a dev DB ended up with the type present but the migration not recorded. checkfirst is check-then-create in two steps; the DO block is one atomic statement that tolerates the type already existing.

これは実際の事故の後に Enum.create(bind, checkfirst=True) から置き換えたもの。開発 DB で、型は存在するのにマイグレーションは適用済みと記録されていない状態になった。checkfirst は「確認してから作成」の2段階だが、DO ブロックは型がすでにあっても問題ない1つのアトミックな文。

3. Backfill, then tighten3. バックフィルしてから厳しくする

UPDATE payment SET idempotency_key = gen_random_uuid() WHERE idempotency_key IS NULL
op.alter_column('payment', 'idempotency_key', nullable=False)

· same shape:同じ形：

The column was added as nullable in an earlier migration (90347b38372a), then filled, then made NOT NULL. That's expand → migrate → contract across three migrations.

この列は前のマイグレーション（90347b38372a）で NULL 可として追加され、値を埋めてから NOT NULL にした。3つのマイグレーションにまたがる 拡張 → 移行 → 縮小。

4. A rename that moves data4. データの移動を伴うリネーム

# 1. Backfill BEFORE touching the category row or the table
UPDATE products SET category_id = (Merch) WHERE category_id = (Lightstick)
# 2. Now safe to delete the category row
DELETE FROM categories WHERE name = 'Lightstick'
# 3. Rename the table. Postgres does NOT rename constraints/indexes with it.
op.rename_table("lightstick_details", "merch_details")
ALTER TABLE merch_details RENAME CONSTRAINT ...;  ALTER INDEX ... RENAME TO ...

Its downgrade() restores the schema but openly says it can't restore which products used to be lightsticks, because that information was deleted ().

この downgrade() はスキーマは元に戻すが、どの商品が元々ライトスティックだったかは戻せないと明記している。その情報は削除されたから（）。

5. Adding an enum value5. enum に値を追加する

op.execute(sa.text("ALTER TYPE notification_type_enum ADD VALUE IF NOT EXISTS 'lottery_draw_completed'"))

def downgrade() -> None:
    # Postgres has no ALTER TYPE ... DROP VALUE
    pass

WHYWhy this design, and what it costsこの設計を選んだ理由とそのコスト

  • One concern per migration: if one fails, you know exactly what to fix, and a revert touches only one change. A table and its own trigger ship together, because the trigger is that table's rule.1マイグレーション1関心事：失敗したとき何を直せばよいかがすぐ分かり、取り消しも1つの変更だけで済む。テーブルとその専用トリガーは一緒に出す。トリガーはそのテーブル自身のルールだから。
  • Raw SQL where Alembic has no API: triggers, the generated venues.size column and enum blocks use op.execute. Everything else uses op.* so it stays readable.Alembic に API がない部分は生の SQL：トリガー、生成列 venues.size、enum のブロックは op.execute を使う。それ以外は読みやすさのため op.* を使う。
  • Migrate on boot: simple for one instance, and a deploy can't start new code against an old schema. The cost is covered below.起動時にマイグレーション：インスタンスが1つなら単純で、古いスキーマに対して新しいコードが動くことがない。コストは下で説明する。

WEAK SPOTSKnown gaps you should own自分から説明すべき既知の問題

Migrate on boot doesn't scale out起動時マイグレーションはスケールしない

With two web instances starting together, both run upgrade head at the same time. Postgres locks make one wait, but a long migration also delays startup and health checks. Better: a separate release step (Render's pre-deploy command or a one-off job) that runs once before new instances start.

Web インスタンスが2つ同時に起動すると、両方が同時に upgrade head を実行する。Postgres のロックで片方は待たされるが、長いマイグレーションは起動とヘルスチェックも遅らせる。より良い方法：新しいインスタンスの起動前に1回だけ実行する独立したリリース手順（Render の pre-deploy コマンドや単発のジョブ）。

Locks on big tables大きなテーブルのロック

A backfill UPDATE plus SET NOT NULL in one transaction holds strong locks on the whole table. It's fine at this size, but on millions of rows you'd backfill in batches, add a CHECK (col IS NOT NULL) NOT VALID, validate it separately, and build indexes CONCURRENTLY.

バックフィルの UPDATE と SET NOT NULL を1つのトランザクションで行うと、テーブル全体に強いロックがかかる。今の規模なら問題ないが、数百万行ならバッチでバックフィルし、CHECK (col IS NOT NULL) NOT VALID を追加して別に検証し、インデックスは CONCURRENTLY で作る。

No drift check差分チェックがない

CI proves the chain applies cleanly, but nothing checks that the models and the migrated schema match. Adding alembic check to CI would fail the build when a model changes without a migration.

CI はマイグレーションが問題なく適用できることは証明するが、モデルと適用後のスキーマが一致しているかは確認していない。CI に alembic check を追加すれば、マイグレーションなしでモデルを変えたときにビルドが失敗する。

QUESTIONSPractice questions練習問題

BASICWhy use migrations instead of Base.metadata.create_all()?Base.metadata.create_all() ではなくマイグレーションを使うのはなぜ？

create_all() only creates missing tables. It never alters an existing column, never backfills data, and leaves no history. Migrations are ordered, reviewed, repeatable changes that bring every environment to the same version, including data changes and triggers.

create_all() は存在しないテーブルを作るだけ。既存の列の変更やデータのバックフィルはせず、履歴も残らない。マイグレーションは順番があり、レビューされ、繰り返し実行できる変更で、データ変更やトリガーも含めてすべての環境を同じバージョンにする。

BASICHow do you add a NOT NULL column to a table that already has data?データがあるテーブルに NOT NULL 列を追加するには？

Add it as nullable, backfill existing rows, then set NOT NULL. In this repo payment.idempotency_key went through exactly that: added nullable, filled with gen_random_uuid(), then made NOT NULL. Alternatively, add it with a server default if one value fits every old row.

NULL 可で追加し、既存行をバックフィルしてから NOT NULL にする。このリポジトリの payment.idempotency_key がまさにその流れ：NULL 可で追加、gen_random_uuid() で埋め、NOT NULL にした。古い行すべてに1つの値が合うなら、サーバー側のデフォルト付きで追加する方法もある。

MIDTell me about a migration that went wrong.うまくいかなかったマイグレーションについて話してください。

An enum migration used checkfirst=True. After an interrupted deploy, the dev DB had the enum type but alembic_version didn't record the migration. On every restart, Alembic re-ran it and CREATE TYPE failed, so the container crash-looped. The fix was a DO $$ … EXCEPTION WHEN duplicate_object THEN NULL block, which is atomic and tolerates the type already existing. All enum migrations now use it.

enum のマイグレーションで checkfirst=True を使っていた。デプロイが途中で止まった後、開発 DB には enum 型が存在するのに、alembic_version にはそのマイグレーションが記録されていなかった。再起動のたびに Alembic が再実行して CREATE TYPE が失敗し、コンテナが再起動ループになった。修正は DO $$ … EXCEPTION WHEN duplicate_object THEN NULL ブロックで、アトミックで型がすでにあっても問題ない。今ではすべての enum マイグレーションがこれを使う。

MIDDo you always write a downgrade()? Does it always work?downgrade() は必ず書きますか？必ず動きますか？

I write one, but some changes are one-way. Postgres can't drop an enum value, so that downgrade is a documented no-op. Merging the Lightstick category into Merch deleted the information about which products were lightsticks, so the downgrade restores the schema but not that data, and the code says so. In production, rolling forward with a new fix is usually safer than running a downgrade.

書くが、一方通行の変更もある。Postgres は enum の値を削除できないので、その downgrade は何もしないことを明記している。Lightstick カテゴリーを Merch に統合したときは、どの商品がライトスティックだったかという情報を削除したので、downgrade はスキーマは戻すがそのデータは戻せず、コードにそう書いてある。本番では downgrade を実行するより、新しい修正で前に進める方が通常は安全。

SENIORHow would you rename a column with zero downtime?ダウンタイムなしで列名を変えるには？

Never rename in one step, because old code still running would break. (1) Add the new column. (2) Deploy code that writes both and reads the old one. (3) Backfill in batches. (4) Deploy code that reads the new one. (5) Stop writing the old one. (6) Drop it in a later migration. Each deploy is compatible with the schema before and after it, so a rolling deploy never sees a mismatch.

1回で名前を変えてはいけない。動いている古いコードが壊れるから。(1) 新しい列を追加、(2) 両方に書き古い方を読むコードをデプロイ、(3) バッチでバックフィル、(4) 新しい列を読むコードをデプロイ、(5) 古い列への書き込みをやめる、(6) 後のマイグレーションで古い列を削除。各デプロイは前後どちらのスキーマとも互換があるので、ローリングデプロイ中も不整合が起きない。

SENIORYour migrations run on container start. What happens with 10 instances?マイグレーションがコンテナ起動時に動きます。インスタンスが10個ならどうなりますか？

All ten race to run upgrade head. Postgres DDL locks serialize them, and the later ones find nothing to do, so the data is safe, but startups stall behind the lock and health checks can fail. Also, instances still running old code may see the new schema before they're replaced. I'd move migrations to one pre-deploy job, keep every migration backward compatible with the previous release, and set a lock_timeout so a migration fails fast instead of blocking traffic.

10個すべてが upgrade head を競って実行する。Postgres の DDL ロックで直列化され、後のものはやることがないのでデータは安全だが、起動がロック待ちで止まり、ヘルスチェックが失敗することがある。また、古いコードのままのインスタンスが置き換わる前に新しいスキーマを見ることもある。マイグレーションはデプロイ前の単発ジョブに移し、各マイグレーションを前のリリースと後方互換にし、lock_timeout を設定してトラフィックを止めずにすぐ失敗させる。
