Topic 04

Authentication: JWT & refresh tokens認証：JWT とリフレッシュトークン

How a fan logs in, stays logged in, and logs out, and where the tokens live.

ファンがログインし、ログイン状態を保ち、ログアウトする仕組みと、トークンの保存場所。

TL;DRSay this in 30 seconds30秒で言えること

  • Passwords are hashed with bcrypt. The plain password is never stored.パスワードは bcrypt でハッシュ化する。平文は保存しない。
  • Login returns a short-lived access JWT in the body and a refresh token in an httpOnly cookie.ログインすると、本文で短命なアクセス JWT、httpOnly Cookie でリフレッシュトークンを返す。
  • The access token is stateless (signature + expiry). The refresh token is stateful: a DB row that can be revoked.アクセストークンはステートレス（署名と有効期限）。リフレッシュトークンはステートフルで、無効化できる DB の行。
  • Each refresh rotates the refresh token. Logout revokes it.リフレッシュのたびにトークンをローテーションする。ログアウトで無効化する。
  • Email-link tokens use a separate secret and a type claim, so a verify link can't reset a password.メールリンク用トークンは別の秘密鍵と type クレームを使うので、確認用リンクでパスワードをリセットできない。

PRIMERThe theory you need必要な理論

Authentication vs. authorization認証と認可

Authentication: who are you? (login, tokens). Authorization: what may you do? (roles, ownership). 401 means "I don't know who you are", 403 means "I know, and the answer is no". Topic 05 covers authorization.

認証：あなたは誰か（ログイン、トークン）。認可：何をしてよいか（ロール、所有権）。401 は「あなたが誰か分からない」、403 は「分かったうえで許可しない」。認可はトピック05。

What a JWT isJWT とは

header.payload.signature, each base64url-encoded. The payload is readable by anyone, so it's signed, not encrypted. The server trusts it because only the server knows the secret (HS256). Because it's self-contained, the server doesn't need a DB lookup to validate it, and it also can't "un-issue" it before it expires.

header.payload.signature で、それぞれ base64url エンコードされている。ペイロードは誰でも読めるので、暗号化ではなく署名されているだけ。秘密鍵（HS256）を知っているのはサーバーだけなので、サーバーはそれを信頼できる。自己完結しているので検証に DB を引く必要がないが、期限前に「発行を取り消す」こともできない。

Why two tokensなぜトークンが2つあるのか

Access tokenアクセストークンRefresh tokenリフレッシュトークン
Lifetime有効期間Minutes数分Days数日
Sent送信先Every API call (Authorization: Bearer)毎回の API 呼び出し（Authorization: Bearer）Only to /refresh (cookie)/refresh にだけ（Cookie）

You get cheap checks on every request and a way to end sessions, without a DB lookup per call.

毎回の確認は軽く、セッションを終わらせる手段もあり、しかも呼び出しごとに DB を引かずに済む。

1. Login1. ログイン

@router.post("/login")
def login(form_data: OAuth2PasswordRequestForm = Depends(), _: None = Depends(rate_limit(10, 60, ip_key)), ...):
    db_user = AuthService.authenticate_user(db, form_data.username, form_data.password)
    if not db_user:
        raise ApiHTTPException(status_code=401, detail="Invalid credentials", code="invalid_credentials")
    token = AuthService.create_tokens(db, db_user)
    response = JSONResponse(content={"access_token": token["access_token"]})
    response.set_cookie("refresh_token", token["refresh_token"],
                        httponly=True, secure=True, samesite="none")

  • httponly: JavaScript can't read the cookie, so an XSS bug can't steal it. secure: HTTPS only. samesite="none": needed because the frontend is on a different site.httponly：JavaScript から読めないので XSS で盗まれない。secure：HTTPS のみ。samesite="none"：フロントエンドが別サイトにあるため必要。

# One active session per user: revoke existing refresh tokens.
db.query(RefreshToken).filter(RefreshToken.user_id == user.id, RefreshToken.revoked == False) \

The refresh token is a random UUID, not a JWT. It only means something because of its DB row, which is exactly what makes it revocable.

リフレッシュトークンは JWT ではなくランダムな UUID。DB の行があって初めて意味を持ち、だからこそ無効化できる。

3. Checking the access token on every request3. 毎回のリクエストでアクセストークンを確認

def get_current_user(request: Request, token: str = Depends(oauth_scheme), db: Session = Depends(get_db)) -> Users:
    user = _user_from_token(token, db)     # decode → uuid(sub) → db.get(Users)
    if not user:
        raise HTTPException(status_code=401, detail="Invalid credentials")
    request.state.user = user              # read later by the rate limiter
    return user

A missing sub, a malformed id or a deleted user all return 401, never a 500. There is also an optional version for public pages that personalize for logged-in fans ().

sub がない、id の形式が不正、ユーザーが削除済み、のいずれも 500 ではなく 401 を返す。ログイン中のファン向けに表示を変える公開ページ用に、任意ログイン版もある（）。

5. Email-link tokens5. メールリンク用トークン

to_encode = {"sub": str(user_id), "type": token_type, "exp": expires}
return jwt.encode(to_encode, settings.JWT_EMAIL_SECRET_KEY, ...)
...
if payload.get("type") != expected_type:
    return None

A separate secret means an email-link token can never pass as a login token. The type claim means a verification link can't be used as a password-reset link. The forgot-password endpoint always answers "If that email is registered…", so it doesn't reveal accounts either.

秘密鍵が別なので、メールリンク用トークンがログイン用トークンとして通ることはない。type クレームがあるので、確認用リンクをパスワードリセットに使えない。パスワード再設定の窓口は常に「そのメールが登録されていれば…」と答えるので、アカウントの有無も明かさない。

WHYWhy this design, and what it costsこの設計を選んだ理由とそのコスト

  • Refresh token in an httpOnly cookie: the long-lived secret is never visible to JavaScript, so an XSS bug can't steal it. Where the frontend keeps the short-lived access token is the frontend's choice (docs/api-spec.md); keeping it in memory rather than localStorage is the safer option.リフレッシュトークンは httpOnly Cookie：長寿命の秘密は JavaScript から見えないので、XSS で盗まれない。短命なアクセストークンをどこに置くかはフロントエンド側の判断（docs/api-spec.md）で、localStorage よりメモリに置く方が安全。
  • Cost of SameSite=None: the browser sends the cookie on cross-site requests, so CSRF matters for /refresh. It's limited because /refresh only returns a token in the response body, which a cross-site attacker can't read under CORS.SameSite=None のコスト：ブラウザはクロスサイトのリクエストにも Cookie を送るので、/refresh には CSRF の考慮が必要。ただし /refresh はトークンをレスポンス本文で返すだけで、CORS により他サイトの攻撃者は読めないので影響は限定的。
  • bcrypt: slow on purpose, with a per-password salt, so a leaked table is expensive to crack. It's also CPU-heavy, which is one more reason login is rate-limited.bcrypt：意図的に遅く、パスワードごとにソルトを持つので、漏れたテーブルを解読するのが高くつく。CPU 負荷も高いので、ログインをレート制限する理由の1つでもある。

WEAK SPOTSKnown gaps you should own自分から説明すべき既知の問題

bugs.md #20

Refresh tokens stored in plain text, and one session per user. A DB leak hands out working refresh tokens; store a SHA-256 hash instead and compare hashes. Also, create_tokens revokes all of a user's tokens, so logging in on a phone logs out the laptop.

リフレッシュトークンが平文で保存され、1ユーザー1セッション。DB が漏れると有効なリフレッシュトークンがそのまま使われる。代わりに SHA-256 のハッシュを保存して比較すべき。また create_tokens がユーザーの全トークンを無効化するので、スマホでログインするとノートPCがログアウトされる。

bugs.md #18, #19

Password changes don't end sessions. Changing a password doesn't revoke refresh tokens (reset does), and a reset link can be reused until it expires because nothing marks it used. Fix: revoke on change, and bind the reset token to a jti or the current password hash.

パスワード変更でセッションが終わらない。パスワード変更ではリフレッシュトークンが無効化されず（リセットではされる）、リセット用リンクも使用済みにならないため期限まで再利用できる。対策：変更時に無効化し、リセット用トークンを jti か現在のパスワードハッシュに結び付ける。

Other things to mentionその他言及すべき点

No refresh-token reuse detection: a stolen, already-rotated token just fails, and nobody is alerted. JWT_REFRESH_SECRET_KEY is a required setting but nothing uses it (). /register answers "Email already registered", which does reveal accounts; rate limiting reduces that risk.

リフレッシュトークンの再利用検知がない：盗まれてローテーション済みのトークンは失敗するだけで、誰にも通知されない。JWT_REFRESH_SECRET_KEY は必須設定だが使われていない（）。/register は「Email already registered」と返すのでアカウントの有無が分かる。レート制限でリスクを下げている。

QUESTIONSPractice questions練習問題

BASICHow do you store passwords?パスワードはどう保存していますか？

Hashed with bcrypt through passlib. bcrypt adds a random salt per password and is deliberately slow, so identical passwords get different hashes and brute-forcing a leaked table is expensive. Login compares with verify_password; the plain password is never stored or logged.

passlib 経由で bcrypt によりハッシュ化している。bcrypt はパスワードごとにランダムなソルトを付け、意図的に遅いので、同じパスワードでもハッシュが異なり、漏れたテーブルの総当たりは高くつく。ログイン時は verify_password で比較し、平文は保存もログ出力もしない。

BASICWhy not keep the access token in localStorage?アクセストークンを localStorage に保存しないのはなぜ？

Any script on the page can read localStorage, so one XSS bug leaks the token. Keeping the short-lived access token in memory and the long-lived refresh token in an httpOnly cookie means scripts can't read the long-lived secret. After a reload, the app calls /refresh to get a new access token.

localStorage はページ上のどのスクリプトからも読めるので、XSS のバグが1つあればトークンが漏れる。短命なアクセストークンはメモリに、長寿命のリフレッシュトークンは httpOnly Cookie に置けば、長寿命の秘密はスクリプトから読めない。再読み込み後は /refresh を呼んで新しいアクセストークンを取得する。

MIDJWTs are stateless. How do you log someone out?JWT はステートレスです。どうやってログアウトさせますか？

Logout revokes the refresh token row and clears the cookie, so no new access tokens can be issued. The current access token stays valid until it expires, which is why its lifetime is short. If instant revocation were required, I'd add a denylist of token ids (jti) in Redis with a TTL equal to the token's remaining life, or a per-user "tokens valid after" timestamp.

ログアウトでリフレッシュトークンの行を無効化し Cookie を消すので、新しいアクセストークンは発行されない。今のアクセストークンは期限まで有効なので、有効期間を短くしている。即時失効が必要なら、トークン id（jti）の拒否リストを残り期間と同じ TTL で Redis に置くか、ユーザーごとに「この時刻以降に発行されたトークンのみ有効」というタイムスタンプを持つ。

MIDWhat is refresh-token rotation, and what does it protect against?リフレッシュトークンのローテーションとは？何を防ぎますか？

Every refresh issues a new refresh token and revokes the old one, so a stolen token is only useful until the real user refreshes. The stronger version adds reuse detection: if a revoked token is presented, assume theft and revoke the whole token family. i-dolly rotates but doesn't detect reuse yet.

リフレッシュのたびに新しいリフレッシュトークンを発行し、古いものを無効化する。盗まれたトークンは本人が次にリフレッシュするまでしか使えない。さらに強い方法は再利用検知で、無効化済みのトークンが提示されたら盗難とみなし、そのトークン系列をすべて無効化する。i-dolly はローテーションはしているが、再利用検知はまだない。

SENIORYour DB is leaked. What can the attacker do with the auth tables?DB が漏洩しました。攻撃者は認証テーブルで何ができますか？

Passwords: only bcrypt hashes, so they'd have to crack them slowly. Refresh tokens: today they're stored in plain text (bug #20), so any unexpired, unrevoked token lets them mint access tokens. Fix: store sha256(token) and compare the hash; a random token has enough entropy that a fast hash is fine. Also rotate the JWT secret, which invalidates all access tokens at once.

パスワード：bcrypt のハッシュだけなので、時間をかけて解読するしかない。リフレッシュトークン：現状は平文で保存されている（バグ #20）ので、期限内で未失効のものがあればアクセストークンを発行できてしまう。対策：sha256(token) を保存してハッシュで比較する。ランダムなトークンはエントロピーが十分なので高速なハッシュで問題ない。さらに JWT の秘密鍵をローテーションすれば、全アクセストークンを一度に無効化できる。

SENIORWould you use HS256 or RS256 here?ここでは HS256 と RS256 のどちらを使いますか？

HS256 is fine while one service both issues and verifies tokens: one shared secret, fast. RS256 matters when other services need to verify tokens without being able to create them: they get the public key only. If i-dolly split into services, or used an external identity provider, I'd switch to RS256 with a JWKS endpoint and key rotation.

1つのサービスがトークンの発行と検証の両方を行う間は HS256 で十分：共有の秘密鍵が1つで速い。RS256 が必要になるのは、他のサービスがトークンを作れないまま検証だけしたい場合で、公開鍵だけを渡せばよい。i-dolly をサービス分割したり外部の ID プロバイダーを使ったりするなら、JWKS エンドポイントと鍵ローテーション付きで RS256 に切り替える。
