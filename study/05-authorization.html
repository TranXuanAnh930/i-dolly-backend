Topic 05

Authorization: RBAC & company scoping認可：RBAC と会社スコープ

Who may do what: three roles, managers fenced into their own company, and fans who can only see their own data.

誰が何をできるか：3つのロール、自社の範囲に限定されたマネージャー、自分のデータだけを見られるファン。

TL;DRSay this in 30 seconds30秒で言えること

  • Three roles: admin (everything), manager (their own company's content), fan (buys and applies).3つのロール：admin（すべて）、manager（自社のコンテンツ）、fan（購入と応募）。
  • Two checks, in two places: the router checks the role (require_manager_or_admin); the service checks the company (_manager_scope_violation).確認は2か所：ルーターでロール（require_manager_or_admin）、サービスで会社（_manager_scope_violation）。
  • Multi-tenancy is a shared schema + company_id, not a schema per company.マルチテナントは会社ごとのスキーマではなく、共有スキーマと company_id。
  • Fan data is scoped at the query level: every lookup filters by user_id, so another fan's id just returns 404.ファンのデータはクエリのレベルで絞る：すべての検索を user_id で絞るので、他のファンの id は 404 になるだけ。
  • Admins and managers can never buy: a service check plus a DB trigger.管理者とマネージャーは購入できない：サービスの確認と DB トリガーの両方で守る。

PRIMERThe theory you need必要な理論

RBAC vs. ownershipRBAC と所有権

Role-based access control answers "can this kind of user do this kind of action?" It's coarse. Ownership / resource checks answer "can this user touch this specific row?" You need both. Most real authorization bugs are missing ownership checks, not wrong roles.

ロールベースアクセス制御は「この種類のユーザーはこの種類の操作をできるか？」に答える。大まかな確認。所有権・リソースの確認は「このユーザーはこの特定の行を触れるか？」に答える。両方が必要。実際の認可バグの多くはロールの誤りではなく、所有権の確認漏れ。

IDORIDOR（安全でない直接オブジェクト参照）

Insecure Direct Object Reference: the API takes an id from the client and loads that row without checking it belongs to the caller. GET /orders/42 returns someone else's order. The fix is to put the owner in the query itself: WHERE id = :id AND user_id = :me.

IDOR：API がクライアントから id を受け取り、呼び出し元の所有かを確認せずにその行を読み込むこと。GET /orders/42 で他人の注文が返ってくる。対策は、クエリ自体に所有者を入れること：WHERE id = :id AND user_id = :me。

2. Role check in the router2. ルーターでロールを確認

def require_manager_or_admin(current_user: Users = Depends(get_current_user)) -> Users:
    """Require an admin or manager role. Company scoping is checked in each service."""
    if current_user.role not in (UserRole.admin, UserRole.manager):
        raise HTTPException(status_code=403, detail="Manager or admin access required")
    return current_user

3. Company check in the service3. サービスで会社を確認

def _manager_scope_violation(current_user: Users, company_id: uuid.UUID) -> bool:
    return current_user.role == UserRole.manager and current_user.company_id != company_id

db_group = db.get(Group, id)
if not db_group:
    raise NotFoundError("Group not found")
if GroupService._manager_scope_violation(current_user, db_group.company_id):
    raise ForbiddenError("Managers can only manage groups for their own company")

·

The company comes from the row in the DB, never from the request body, so a manager can't claim someone else's company. The service has the row; the router doesn't, which is why this check lives in the service.

会社はリクエスト本文ではなくDB の行から取るので、マネージャーが他社を名乗ることはできない。行を持っているのはルーターではなくサービスなので、この確認はサービスに置く。

4. Products have no company_id4. 商品には company_id がない

def _manager_scope_violation(db, current_user, product_id) -> bool:
    if current_user.role != UserRole.manager:
        return False
    company_id = ProductService._resolve_product_company_id(db, product_id)  # via album/merch → idol/group
    if company_id is None:
        return False  # ownerless product - any manager may manage it
    return current_user.company_id != company_id

Ownership is derived: product → album or merch details → idol or group → company. Managers also can't change a product's price after creation; only admins can ().

所有者は導出する：商品 → アルバムまたはグッズの詳細 → アイドルまたはグループ → 会社。マネージャーは作成後に商品価格を変えられず、変えられるのは管理者だけ（）。

5. Fan data: owner in the query5. ファンのデータ：クエリに所有者を入れる

cart = db.query(Cart).filter(Cart.id == cart_id, Cart.user_id == user_id).first()
if not cart:
    return None    # someone else's cart looks exactly like a missing one → 404

·

Returning 404 rather than 403 for another user's row means an attacker can't even learn the id exists.

他人の行に 403 ではなく 404 を返すので、攻撃者はその id が存在するかどうかさえ分からない。

6. Cached pages, scoped per request6. キャッシュしたページをリクエストごとに絞る

@router.get("/manager-groups-page")
def get_manager_groups_page_data(current_user = Depends(require_manager_or_admin), ...):
    return GroupService.scope_manager_groups_page(CacheService.get_cached_manager_groups_page(db), current_user)

# The cached page holds every company's rows; managers get only their own company's.

·

One cache entry serves every manager, and the filter runs after the cache. The alternative, a cache key per company, would be safer against a forgotten filter but multiplies cache entries and invalidations.

1つのキャッシュを全マネージャーで共有し、キャッシュの後でフィルタをかける。会社ごとにキャッシュキーを分ければフィルタ忘れには強いが、キャッシュ数と削除処理が増える。

7. Proving it7. 証明

69 integration tests hit real HTTP routes with real JWTs for each role: unauthenticated → 401, fan → 403, wrong-company manager → 403, own-company manager → 200 ().

69個の統合テストが、ロールごとに本物の JWT で本物の HTTP ルートを呼ぶ：未認証 → 401、ファン → 403、他社のマネージャー → 403、自社のマネージャー → 200（）。

WHYWhy this design, and what it costsこの設計を選んだ理由とそのコスト

  • Shared schema: one set of migrations, easy cross-company reporting for admins, and a handful of companies don't justify a schema each. The cost: isolation depends on every service remembering its check.共有スキーマ：マイグレーションは1セットで、管理者の会社横断レポートも簡単。会社が数社なら会社ごとのスキーマは割に合わない。コスト：分離は各サービスが確認を忘れないことに依存する。
  • Reads stay public: idol and concert listings are public by design, so only writes and manager pages are scoped.読み取りは公開：アイドルや公演の一覧は意図的に公開なので、スコープを絞るのは書き込みとマネージャー用ページだけ。
  • Admins can't buy: staff accounts buying scarce tickets is a fairness problem, so it gets a DB trigger backstop, not just a UI rule.管理者は購入不可：スタッフのアカウントが希少なチケットを買うのは公平性の問題なので、UI のルールだけでなく DB トリガーでも守る。

WEAK SPOTSReal bugs this codebase hadこのコードに実際にあったバグ

bugs.md #3, #28 (fixed)（修正済み）

IDORs. Removing a cart item filtered only by the cart id, so any fan could delete another fan's item. GET /shipping_addresses/fetch_byid had no login at all, and its sibling update/delete filtered by user_id == user_id (the argument compared with itself, always true) instead of ShippingAddress.user_id == user_id. Both are fixed by putting the caller's id in the query. That second one is a great story: the code looked scoped.

IDOR。カートの商品削除はカート id だけで絞っていたので、どのファンでも他人の商品を削除できた。GET /shipping_addresses/fetch_byid はログイン不要で、同じ系統の更新・削除は user_id == user_id（常に真）で絞っていた。どちらも呼び出し元の id をクエリに入れて修正した。2つ目は話のネタとして最適で、コードは一見スコープされて見えた。

bugs.md #29 (fixed)（修正済み）

Manager pages had no auth. Six manager-*-page endpoints took no auth dependency, and two filtered by a company_id sent by the client. Now they require a manager role, are rate-limited, and scope by the caller's company on the server.

マネージャー用ページに認証がなかった。6つの manager-*-page エンドポイントに認証がなく、2つはクライアントが送る company_id で絞っていた。現在はマネージャーロールを要求し、レート制限をかけ、サーバー側で呼び出し元の会社に絞っている。

Still open未解決

Ownerless products (plain merch with no idol or group) can be edited or deleted by any manager, and product delete is a hard delete (bug #2). Scoping lives only in code, so a new service that forgets _manager_scope_violation leaks silently. Postgres Row-Level Security would be a DB-level backstop.

所有者のない商品（アイドルやグループに紐付かない普通のグッズ）はどのマネージャーでも編集・削除でき、商品削除は物理削除（バグ #2）。スコープはコードにしかないので、_manager_scope_violation を忘れた新しいサービスは黙ってデータを漏らす。Postgres の行レベルセキュリティを DB 側の最後の砦にできる。

QUESTIONSPractice questions練習問題

BASICHow do you stop one fan from reading another fan's orders?あるファンが他のファンの注文を見られないようにするには？

The user id comes from the verified token, never from the request, and every query includes it: WHERE id = :order_id AND user_id = :me. If the row isn't theirs, the query finds nothing and the API returns 404, the same as for an id that doesn't exist.

ユーザー id はリクエストからではなく検証済みのトークンから取り、すべてのクエリに含める：WHERE id = :order_id AND user_id = :me。自分の行でなければ何も見つからず、存在しない id と同じく 404 を返す。

BASICWhat's the difference between 401 and 403 in your API?あなたの API での 401 と 403 の違いは？

401: no valid token, so we don't know who you are. 403: we know who you are, but your role or company doesn't allow this, for example a fan calling a manager endpoint or a manager editing another company's idol.

401：有効なトークンがなく、誰か分からない。403：誰かは分かるが、ロールや会社がそれを許さない。例えばファンがマネージャー用エンドポイントを呼ぶ、マネージャーが他社のアイドルを編集する場合。

MIDWhy not check the company in a FastAPI dependency?会社の確認を FastAPI の依存関係で行わないのはなぜ？

The company isn't in the request; it's on the row being changed, and sometimes it's several joins away (a product's company comes through its album and idol). The service loads that row anyway, so it's the natural place. The dependency only checks what it can see: the caller's role.

会社はリクエストの中ではなく、変更対象の行にある。しかも商品の会社はアルバムやアイドルを経由するなど、何段もの JOIN の先にあることもある。サービスはどのみちその行を読み込むので、そこが自然な場所。依存関係は自分に見えるもの、つまり呼び出し元のロールだけを確認する。

MIDTell me about an authorization bug you found.見つけた認可のバグについて話してください。

The shipping-address update and delete filtered by user_id == user_id: the Python argument compared with itself, which is always True, instead of ShippingAddress.user_id == user_id. It looked scoped in review, but any logged-in fan could edit or delete any address by id. The fix compared the column to the caller's id, and the sibling fetch_byid route got a login requirement it was missing. The lesson: test that user A gets 404 on user B's resource, don't just read the filter.

配送先の更新と削除が ShippingAddress.user_id == user_id ではなく user_id == user_id で絞っていた。Python の引数を自分自身と比べているので常に True になる。レビューではスコープされているように見えたが、ログイン中のファンなら誰でも id を指定して任意の住所を編集・削除できた。修正では列を呼び出し元の id と比較し、同じ系統の fetch_byid ルートにも欠けていたログイン要求を追加した。教訓：フィルタを読むだけでなく、ユーザー A がユーザー B のリソースで 404 になることをテストする。

SENIORHow would you make tenant isolation safer than "remember to check"?「確認を忘れない」より安全なテナント分離にするには？

(1) Postgres Row-Level Security: set app.company_id per request with SET LOCAL, and a policy USING (company_id = current_setting('app.company_id')::uuid), so a forgotten filter returns nothing instead of leaking. (2) A repository base class that always adds the tenant filter. (3) A test that loops over every manager route and asserts a wrong-company manager gets 403. RLS is the strongest because it protects scripts and raw SQL too.

(1) Postgres の行レベルセキュリティ：リクエストごとに SET LOCAL で app.company_id を設定し、USING (company_id = current_setting('app.company_id')::uuid) のポリシーを付ける。フィルタを忘れても漏れずに何も返らない。(2) テナントのフィルタを必ず付けるリポジトリの基底クラス。(3) すべてのマネージャー用ルートを回して、他社のマネージャーが 403 になることを確認するテスト。RLS はスクリプトや生の SQL も守るので最も強い。
