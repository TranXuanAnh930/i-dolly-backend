Topic 06

Transactions & concurrencyトランザクションと並行性

How i-dolly stops two fans from buying the same last seat, and how you prove it works.

2人のファンが同じ最後の1席を買えないようにする仕組みと、それが正しく動くことの証明方法。

TL;DRSay this in 30 seconds30秒で言えること

  • Each checkout is one transaction with one commit at the end. Any error rolls back everything.各チェックアウトは最後に1回だけコミットする1つのトランザクション。どこかで失敗すれば全部ロールバックされる。
  • The scarce row (product stock, ticket tier) is locked with SELECT … FOR UPDATE before it is checked, so a second buyer waits and then sees the updated number.在庫やチケット枠などの行は、確認する前に SELECT … FOR UPDATE でロックする。2人目は待たされ、更新後の値を読む。
  • Multiple rows are locked in a fixed order (ORDER BY id) to avoid deadlocks.複数行は決まった順番（ORDER BY id）でロックし、デッドロックを防ぐ。
  • Rules are checked twice: in the service (clear error) and by a Postgres trigger or UNIQUE constraint (backstop).ルールは2回確認する。サービス層（分かりやすいエラー）と、Postgres のトリガーや UNIQUE 制約（最後の砦）。
  • Races are tested with real threads against real Postgres, released together by a barrier.競合は実際の Postgres に対して実スレッドを Barrier で同時に走らせてテストしている。

PRIMERThe theory you need必要な理論

The check-then-act race「確認してから更新」の競合

Postgres runs at READ COMMITTED by default: each statement sees data committed before it started. So "read stock → check it → write stock" is not safe. Two transactions can both read quantity = 1, both pass the check, and both sell. This is a lost update.

Postgres のデフォルト分離レベルは READ COMMITTED で、各文はその開始時点でコミット済みのデータを読む。そのため「在庫を読む → 確認 → 書き込む」は安全ではない。2つのトランザクションが両方 quantity = 1 を読み、両方とも確認を通過して販売してしまう。これが更新の消失（lost update）。

3. Lottery apply vs. draw: FOR SHARE vs. FOR UPDATE3. 抽選応募と抽選実行：FOR SHARE と FOR UPDATE

# FOR SHARE: the draw locks campaigns FOR UPDATE, so an apply and a draw can't interleave.
campaign = db.get(LotteryCampaign, campaign_id, with_for_update={"read": True}, populate_existing=True)

· draw side:抽選側：

Thousands of fans apply at once, so applies take a shared lock and don't block each other. The draw takes an exclusive lock, so it waits for in-flight applies, and any apply that arrives during the draw waits, then re-reads status = drawn and is rejected. Without this, an entry could land after the draw and stay pending forever.

大量のファンが同時に応募するので、応募は共有ロックを取り、互いにブロックしない。抽選は排他ロックを取るため、処理中の応募が終わるのを待つ。抽選中に来た応募は待たされた後に status = drawn を読み直して拒否される。これがないと、抽選後に入った応募が永遠に pending のまま残る。

Interview trap面接の落とし穴

A trigger that counts rows is not race-proof on its own. Under READ COMMITTED it can't see another transaction's uncommitted insert, so two parallel inserts can both count 0. The trigger catches bugs and direct SQL writes. The row locks are what stop the race.

行数を数えるトリガーは単体では競合に対して安全ではない。READ COMMITTED では他のトランザクションの未コミットの INSERT が見えないため、並行する2つの INSERT が両方とも 0 件と数えうる。トリガーはバグや直接の SQL 書き込みを防ぐもので、競合を防いでいるのは行ロック。

5. Proving it: the race harness5. 証明：競合テスト用ハーネス

barrier = threading.Barrier(len(fns))
def _run(index, fn):
    barrier.wait()  # every thread blocks here until all of them have arrived
    outcomes[index].result = fn()

· used by使用例： · ·

Three fans race for 1 unit, and the test asserts exactly one 200, two 400s and final stock 0. It uses real OS threads, not asyncio, because the DB layer is synchronous and only real blocking on real Postgres locks reproduces the race. A race test is only useful if it fails when the lock is removed. Exercise 2 below checks that.

3人のファンが在庫1個を奪い合い、200 がちょうど1回、400 が2回、最終在庫が 0 であることを確認する。asyncio ではなく実際の OS スレッドを使うのは、DB 層が同期処理で、実際の Postgres ロックで本当にブロックさせないと競合を再現できないから。競合テストはロックを外したときに失敗しなければ意味がない。下の演習2で確かめよう。

WHYWhy this design, and what it costsこの設計を選んだ理由とそのコスト

  • Pessimistic over optimistic: a ticket drop is the worst case for optimistic locking, where most attempts would conflict and retry. Locking makes losers wait a few milliseconds and then fail cleanly.楽観的より悲観的を選んだ理由：チケット発売は楽観的ロックにとって最悪のケースで、ほとんどの試行が衝突して再試行になる。ロックなら負けた側は数ミリ秒待って、きれいに失敗する。
  • Not a single atomic UPDATE: checkout also creates an order, items and a payment, and checks the resale cap. That logic needs a stable view of the row, so a lock fits better.単一のアトミック UPDATE にしない理由：チェックアウトでは注文・明細・決済の作成や転売上限の確認も行う。このロジックには行の安定した状態が必要なので、ロックの方が合う。
  • Cost: every buyer of one hot item is serialized on one row. Throughput for that item is about 1 / (transaction time), so transactions must stay short. The pool is only 5 + 5 connections (), so a long lock also starves other requests.コスト：人気商品1つの購入者は全員1行の上で直列化される。その商品のスループットはおよそ 1 / トランザクション時間なので、トランザクションは短く保つ必要がある。接続プールは 5 + 5 本だけなので（）、長いロックは他のリクエストも詰まらせる。

WEAK SPOTSKnown gaps you should own自分から説明すべき既知の問題

bugs.md #8

Network call while holding locks. finalize_paypal_payment calls PayPal's capture API while holding FOR UPDATE on payment, ticket type and products (). A slow gateway holds the locks for up to 10 s. If PayPal captures but our commit fails, the fan is charged and the DB says pending. Fix: keep transactions short (reserve → commit → call gateway → finalize in a new transaction), plus webhook reconciliation.

ロックを保持したままのネットワーク呼び出し。finalize_paypal_payment は payment・ticket type・products に FOR UPDATE をかけたまま PayPal の capture API を呼ぶ（）。ゲートウェイが遅いと最大10秒ロックが続く。PayPal 側で決済が完了したのにコミットが失敗すると、請求済みなのに DB は pending のままになる。対策：トランザクションを短くする（確保 → コミット → ゲートウェイ呼び出し → 別トランザクションで確定）と、Webhook による突き合わせ。

bugs.md #13

Resale cap checked before the lock. The 3-unit sum runs before any lock is taken (), and album checkout does not lock the user row. Two parallel checkouts by the same fan can both pass, and the trigger has the same READ COMMITTED blind spot. Fix: lock the user row first, as ticket checkout already does.

転売上限の確認がロック前に行われる。3個上限の合計はロックを取る前に計算され（）、アルバム購入ではユーザー行をロックしない。同じファンの並行チェックアウトが両方通過しうるうえ、トリガーにも同じ READ COMMITTED の死角がある。対策：チケット購入と同じく、最初にユーザー行をロックする。

QUESTIONSPractice questions練習問題

BASICWhat is a race condition? Give one from this project.競合状態とは？このプロジェクトの例を挙げてください。

The result depends on the timing of concurrent operations. Example: two fans check out the last album. Both read quantity 1, both pass the stock check, and both orders succeed, so we oversell. i-dolly prevents it by locking the product row before the check.

並行処理のタイミングによって結果が変わる状態。例：2人のファンが最後のアルバムを同時に購入すると、両方が在庫1を読んで確認を通過し、両方の注文が成功して売り越しになる。i-dolly では確認の前に商品行をロックして防いでいる。

BASICWhat does SELECT … FOR UPDATE do, and when is the lock released?SELECT … FOR UPDATE は何をしますか？ロックはいつ解放されますか？

It reads rows and takes an exclusive row lock on them. Other transactions that try to lock or modify those rows wait. Plain SELECTs still read the last committed version. The lock is released only at COMMIT or ROLLBACK.

行を読み、その行に排他ロックをかける。同じ行をロックまたは更新しようとする他のトランザクションは待たされる。通常の SELECT は最後にコミットされた値を読める。ロックは COMMIT か ROLLBACK のときにだけ解放される。

MIDWhy do you lock products with ORDER BY id?なぜ商品を ORDER BY id でロックするのですか？

To prevent deadlocks. If transaction 1 locks A then B, and transaction 2 locks B then A, each ends up holding one lock and waiting for the other. Postgres detects this and kills one of them. With a global order, both try A first and one simply waits.

デッドロックを防ぐため。トランザクション1が A→B、トランザクション2が B→A の順でロックすると、互いに相手のロックを待ち続ける。Postgres はこれを検知して片方を強制終了する。全体で順番を決めておけば、両方とも A から取ろうとするので片方が待つだけで済む。

MIDWhat bug does populate_existing() prevent?populate_existing() はどんなバグを防ぎますか？

SQLAlchemy's session keeps one object per primary key (the identity map). The resale-cap query had already loaded those products without a lock. When the locked query runs, the ORM would normally hand back the cached objects and ignore the fresh column values, so the stock check would use stale numbers. populate_existing() overwrites them with what the locked SELECT returned.

SQLAlchemy のセッションは主キーごとに1つのオブジェクトを保持する（identity map）。転売上限のクエリでその商品はロックなしですでに読み込まれている。ロック付きクエリを実行しても、ORM は通常キャッシュ済みのオブジェクトを返して新しい値を無視するため、在庫確認が古い値で行われる。populate_existing() はロック付き SELECT の結果で上書きする。

MIDWhy does lottery apply use FOR SHARE and not FOR UPDATE?抽選応募はなぜ FOR UPDATE ではなく FOR SHARE なのですか？

Applies only need to stop the draw from running at the same time. They don't need to stop each other. FOR SHARE locks are compatible with each other but conflict with the draw's FOR UPDATE. So thousands of applies run in parallel, and the draw gets a clean cut-off.

応募が防ぎたいのは抽選との同時実行だけで、応募同士を止める必要はない。FOR SHARE 同士は共存できるが、抽選の FOR UPDATE とは衝突する。そのため大量の応募は並行して動き、抽選は明確な締め切りを得られる。

MIDYou check rules in the service and in a trigger. Isn't that duplication?サービス層とトリガーの両方でルールを確認するのは重複では？

On purpose. The service check gives a fast, specific error message. The trigger guarantees the rule for every writer: a future endpoint, an admin script, or a bug. The trigger is not the race fix, though. Under READ COMMITTED it can't see uncommitted rows, so locks still do that job.

意図的な重複。サービス層は速く具体的なエラーを返す。トリガーは、将来のエンドポイントや管理スクリプト、バグなど、どこから書き込まれてもルールを保証する。ただしトリガーは競合対策ではない。READ COMMITTED では未コミットの行が見えないので、競合はロックで防ぐ。

SENIOR50,000 fans hit "buy" at 10:00. Would you keep the row lock?10時に5万人が「購入」を押します。行ロックのままで良いですか？

For correctness, yes. For throughput, it's the bottleneck: one hot row serializes every buyer, and with a 10-connection pool most requests queue. Options: (1) a single atomic UPDATE … WHERE sold < total RETURNING to shorten the critical section; (2) a waiting-room queue in front of checkout; (3) pre-decrement a counter in Redis and only send winners to Postgres; (4) split the stock across N rows and pick one at random. That's the reason i-dolly uses a lottery for hot concerts: it turns a stampede into a batch job.

正しさの面ではロックで良い。ただしスループットの面ではボトルネックになる。1つの人気行で全購入者が直列化され、接続プールが10本なのでほとんどのリクエストは待ち行列に入る。選択肢：(1) 単一のアトミックな UPDATE … WHERE sold < total RETURNING でクリティカルセクションを短くする、(2) 購入の前に待合室（キュー）を置く、(3) Redis のカウンターを先に減らし、当選者だけを Postgres に送る、(4) 在庫を N 行に分けてランダムに選ぶ。i-dolly が人気公演に抽選を使うのはこのためで、殺到をバッチ処理に変えられる。

SENIORWhat's wrong with calling a payment API inside the transaction?トランザクション内で決済 API を呼ぶと何が問題ですか？

Two problems. (1) Locks and a pooled connection are held for the whole network round-trip, which kills throughput. (2) There's no atomic commit across two systems: PayPal can succeed while our commit fails, leaving a charged fan with a pending order (bug #8). The fix: reserve and commit, call the gateway outside any transaction, then finalize in a second short transaction keyed by an idempotency key. Also reconcile from webhooks, and apply the webhook's state instead of re-capturing.

問題は2つ。(1) ネットワーク往復の間ずっとロックと接続を保持するので、スループットが落ちる。(2) 2つのシステムにまたがるアトミックなコミットはできない。PayPal 側は成功し、こちらのコミットは失敗すると、請求済みなのに注文が pending のまま残る（バグ #8）。対策：確保してコミットし、トランザクション外でゲートウェイを呼び、冪等キーを使った2つ目の短いトランザクションで確定する。さらに Webhook で突き合わせ、再キャプチャせずに Webhook の状態を反映する。

SENIORHow do you know your locking actually works?ロックが本当に機能していると、どうやって分かりますか？

Integration tests against real Postgres. run_concurrently starts N threads, each with its own session and connection, and releases them together with a threading.Barrier so they really contend. The tests assert on outcomes and final state: exactly one success, stock 0. A good race test must also fail when the lock is removed, so you know it isn't passing by accident (bugs.md records this for the lottery apply-window test). Mocks or SQLite couldn't show this, because the behavior lives in Postgres's lock manager.

実際の Postgres に対する統合テスト。run_concurrently は N 個のスレッドを起動し（それぞれ独自のセッションと接続を持つ）、threading.Barrier で同時にスタートさせて本当に競合させる。成功がちょうど1件で最終在庫が 0、といった結果と最終状態を検証する。良い競合テストはロックを外すと失敗する必要があり、それで偶然通っているのではないと分かる（抽選の応募期間テストについては bugs.md に記録がある）。モックや SQLite では確認できない。この挙動は Postgres のロックマネージャーにあるから。
