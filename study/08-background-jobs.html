Topic 08

Background jobs & side effectsバックグラウンドジョブと副作用

What runs outside the request (the lottery draw, emails), and the hard part: side effects that happen after a commit.

リクエストの外で動くもの（抽選、メール）と、難しい部分：コミットの後に起きる副作用。

TL;DRSay this in 30 seconds30秒で言えること

  • Celery with Redis as broker runs two kinds of task: the lottery draw and email sending.Redis をブローカーにした Celery が、抽選とメール送信の2種類のタスクを実行する。
  • The draw endpoint checks permissions synchronously, then enqueues the draw and returns immediately.抽選のエンドポイントは権限を同期的に確認してから抽選をキューに入れ、すぐに返す。
  • In-app notifications are rows written in the same transaction as the change, so they commit or roll back together.アプリ内通知は変更と同じトランザクションで書く行なので、一緒にコミットまたはロールバックされる。
  • Emails are sent only after the commit, so a failed commit never sends a confirmation.メールはコミット後にだけ送るので、コミットが失敗したのに確認メールが届くことはない。
  • The weak spot is the gap after the commit: anything that fails there is a real problem (bug #25).弱点はコミット後の隙間：そこで失敗したものは実際の問題になる（バグ #25）。

PRIMERThe theory you need必要な理論

Why a task queueなぜタスクキューを使うのか

Some work is slow (a draw over thousands of entries), depends on an unreliable third party (an email API), or shouldn't block the user. A queue moves it out of the request: the API produces a message, the broker stores it, and a separate worker process consumes it.

遅い処理（数千件の応募の抽選）、不安定な外部サービスに依存する処理（メール API）、ユーザーを待たせるべきでない処理がある。キューはそれをリクエストの外に出す：API がメッセージを生成し、ブローカーが保存し、別のワーカープロセスが処理する。

The dual-write problem二重書き込み問題

Writing to the DB and sending a message are two systems with no shared transaction. Send before commit and the commit may fail, so you emailed about something that didn't happen. Commit then send, and the send may fail, so it happened and nobody heard. The standard fix is the transactional outbox: write the message as a row in the same transaction, and have a relay publish it later.

DB への書き込みとメッセージ送信は、トランザクションを共有しない2つのシステム。コミット前に送ると、コミットが失敗して起きていないことをメールしてしまう。コミット後に送ると、送信が失敗して起きたのに誰にも伝わらない。標準的な解決策はトランザクショナル・アウトボックス：メッセージを同じトランザクション内で行として書き、後で中継プロセスが送信する。

Delivery guarantees配信の保証

Queues give at-most-once (ack before running: a crash loses the task) or at-least-once (ack after running: a crash runs it again). Exactly-once isn't really available, so tasks should be idempotent: running twice has the same effect as once.

キューは最大1回（実行前に ack：クラッシュするとタスクが消える）か最低1回（実行後に ack：クラッシュすると再実行される）のどちらか。厳密な1回は実質的に存在しないので、タスクは冪等にする：2回実行しても1回と同じ結果になる。

celery_app = Celery("i_dolly", broker=_redis_url, backend=_redis_url,

JSON only (not pickle), so a message can't execute code when it's decoded. Tasks take plain ids as arguments, never ORM objects, and open their own DB session.

JSON のみ（pickle は使わない）なので、メッセージをデコードしたときにコードが実行されることはない。タスクの引数は ORM オブジェクトではなく単純な id で、タスクは自分で DB セッションを開く。

2. Triggering the draw2. 抽選の実行

@router.put("/lottery-draw/{id}", response_model=MessageResponse)
def draw_lottery_for_concert(id, current_user = Depends(require_manager_or_admin), db = Depends(get_db)):
    # Company scoping is checked here, synchronously: a rejection inside the Celery task couldn't
    # be returned to the caller.
    concert = ConcertService.get_concert(db, id)
    ...
    ConcertService.notify_managers_of_draw_trigger(db, concert)
    celery_app.send_task("app.tasks.lottery.draw_lottery", args=[str(id), str(current_user.id)])
    return MessageResponse(msg="Lottery draw task has been scheduled. ...")

send_task by name means the router doesn't import the task module. Validation that the caller needs to see (404, 403) happens before enqueueing; failures inside the task reach managers as notifications instead.

名前で send_task するので、ルーターはタスクのモジュールを import しない。呼び出し元に見せるべき検証（404、403）はキューに入れる前に行い、タスク内の失敗は通知としてマネージャーに届く。

3. The draw task3. 抽選タスク

@celery_app.task(name="app.tasks.lottery.draw_lottery")
def draw_lottery_task(concert_id: str, user_id: str) -> dict:
    db = session()
    try:
        current_user = db.get(Users, uuid.UUID(user_id))
        result = LotteryDrawService.draw_lottery(db, current_user, uuid.UUID(concert_id))
        return result.model_dump(mode="json")
    except Exception:
        db.rollback()
        ConcertService.notify_managers_of_draw_failure(db, concert)
        raise
    finally:
        db.close()

Running it twice is safe: the second run finds no open campaigns and raises. The draw's own state (campaign.status) is what makes it idempotent.

2回実行しても安全：2回目は open のキャンペーンを見つけられず例外になる。抽選自身の状態（campaign.status）が冪等性を生んでいる。

4. Notifications: same transaction4. 通知：同じトランザクション

def create_notification(db, user_id, notification_type, **entity_ids) -> Notification:
    """Add (without committing) a notification, so it commits or rolls back with the caller's
    transaction."""
    notification = Notification(user_id=user_id, type=notification_type, **entity_ids)
    db.add(notification)
    return notification

A fan can never see "you won" for a draw that rolled back. This is the outbox idea applied to in-app messages.

ロールバックされた抽選について「当選しました」とファンに表示されることはない。アウトボックスの考え方をアプリ内メッセージに適用したもの。

· sender:送信側：

This was a real fix (bug #16): emails used to be queued before the commit. In DEBUG mode the sender prints emails instead of calling Resend, so local dev never sends real mail.

これは実際の修正（バグ #16）：以前はコミット前にメールをキューに入れていた。DEBUG モードでは送信側が Resend を呼ばずにメールを表示するだけなので、ローカル開発で本物のメールが送られることはない。

WHYWhy this design, and what it costsこの設計を選んだ理由とそのコスト

  • Celery + Redis: Redis is already there for caching, so no new infrastructure. The cost: cache, rate limiter and queue now share one failure point.Celery と Redis：Redis はキャッシュ用にすでにあるので、新しいインフラが不要。コスト：キャッシュ・レート制限・キューが1つの障害点を共有する。
  • Draw in a worker: the draw can take seconds and holds locks; running it in a request would tie up a web thread and risk a proxy timeout. The manager gets an instant "scheduled" answer and a notification later.抽選はワーカーで：抽選は数秒かかりロックも持つので、リクエスト内で実行すると Web のスレッドを占有し、プロキシのタイムアウトの危険もある。マネージャーにはすぐ「予約済み」と返し、後で通知する。
  • Worker concurrency 1: one task at a time. The worker shares Supabase's connection cap with the web service (), so fewer parallel tasks means fewer connections. It also means one slow email delays the next task.ワーカーの並列数は1：一度に1タスク。ワーカーは Web サービスと Supabase の接続数上限を共有しているので（）、並列数が少ないほど接続も少なくて済む。一方で、遅いメールが1通あると次のタスクも遅れる。

WEAK SPOTSKnown gaps you should own自分から説明すべき既知の問題

bugs.md #25

A committed draw reported as failed. After the draw commits, it busts the cache and notifies managers of completion. If either raises (Redis down, a second commit fails), the task's except tells managers the draw failed, though winners and tickets are saved. The planned fix makes the commit the boundary: the service ends at the commit, and the task runs post-commit steps outside the failure branch, each guarded and logged ().

コミット済みの抽選が失敗と報告される。抽選はコミット後にキャッシュを削除し、マネージャーに完了を通知する。どちらかが例外を出すと（Redis の停止、2回目のコミット失敗）、当選者とチケットは保存済みなのに、タスクの except が抽選の失敗をマネージャーに伝える。予定している修正はコミットを境界にすること：サービスはコミットで終わり、タスクはコミット後の処理を失敗の分岐の外で、それぞれ保護してログを取りながら実行する（）。

bugs.md #11

Redis down after commit → 500 for a successful write. send_task and cache deletes run after the commit with no error handling. A fan can get a 500 for a paid order, retry with a new idempotency key, and pay twice. Plan: best-effort invalidation and dispatch, client timeouts ().

コミット後に Redis が停止 → 成功した書き込みに 500。send_task とキャッシュ削除はコミット後にエラー処理なしで実行される。ファンは支払い済みの注文に 500 を受け取り、新しい冪等キーで再試行して二重に支払うおそれがある。計画：無効化と送信を失敗しても続行する方式にし、クライアントにタイムアウトを設定する（）。

Other gapsその他の不足

Email failures are printed and dropped: no retries, no dead-letter queue. Celery's default acks early, so a worker crash mid-task loses it. The rendered email body, including verification links, is stored in the Redis broker. There's no scheduler (no Celery beat), so nothing expires unpaid lottery wins.

メールの失敗は表示されて捨てられる：再試行もデッドレターキューもない。Celery はデフォルトで早めに ack するので、タスク途中でワーカーが落ちるとタスクが失われる。確認用リンクを含むメール本文がそのまま Redis ブローカーに保存される。スケジューラー（Celery beat）がないので、未払いの当選を失効させる処理がない。

QUESTIONSPractice questions練習問題

BASICWhy does the lottery draw run in Celery and not in the API request?抽選を API リクエストではなく Celery で実行するのはなぜ？

It can take a while with many entries, it holds row locks, and it writes many rows. In a request it would tie up a web thread and a DB connection and could hit the proxy timeout, leaving the manager unsure whether it ran. In a worker, the API answers "scheduled" immediately and the result arrives as a notification.

応募が多いと時間がかかり、行ロックを持ち、大量の行を書く。リクエスト内だと Web のスレッドと DB 接続を占有し、プロキシのタイムアウトに当たって、マネージャーは実行されたのか分からなくなる。ワーカーなら API はすぐ「予約済み」と答え、結果は通知で届く。

BASICWhy pass ids to a task instead of the ORM object?タスクに ORM オブジェクトではなく id を渡すのはなぜ？

The task runs in another process, maybe later. An ORM object is tied to the request's session and can't be serialized to JSON, and even if it could, its data might be stale by the time the task runs. Passing ids makes the task load fresh data in its own session.

タスクは別のプロセスで、場合によっては後で実行される。ORM オブジェクトはリクエストのセッションに結び付いていて JSON にできず、仮にできてもタスク実行時には古くなっているかもしれない。id を渡せば、タスクは自分のセッションで最新のデータを読み込む。

MIDWhen do you send the confirmation email, and why then?確認メールはいつ送りますか？なぜそのタイミング？

After commit_or_raise succeeds. Earlier, a failed commit would mean the fan got "your ticket is confirmed" for a purchase that was rolled back. The remaining risk is the other direction: the commit succeeds but enqueueing fails. For an email that's acceptable, since the order is still visible in the app. For something critical I'd use an outbox.

commit_or_raise が成功した後。それより前だと、コミットが失敗したときに、ロールバックされた購入について「チケットが確定しました」とファンに届いてしまう。残るリスクは逆方向で、コミットは成功したのにキューへの投入が失敗すること。メールならアプリで注文が見えるので許容できる。重要なものならアウトボックスを使う。

MIDWhat happens if the worker crashes in the middle of a draw?抽選の途中でワーカーがクラッシュしたらどうなりますか？

The DB transaction never commits, so Postgres rolls it back and releases the locks: no half-drawn state. With Celery's default early ack, the message is already gone, so the draw doesn't retry. The campaigns are still open, so the manager can trigger it again. Setting acks_late=True would redeliver it automatically, and that's safe because the draw is idempotent.

DB のトランザクションはコミットされないので、Postgres がロールバックしてロックを解放する。中途半端な抽選状態は残らない。Celery のデフォルトは早めの ack なので、メッセージはすでに消えていて抽選は再試行されない。キャンペーンは open のままなので、マネージャーがもう一度実行できる。acks_late=True にすれば自動で再配信され、抽選は冪等なので安全。

SENIORDesign a reliable way to send "you won" emails to 5,000 winners.5,000人の当選者に「当選しました」メールを確実に送る方法を設計してください。

Transactional outbox. In the draw's transaction, insert one outbox row per winner (type, recipient, payload). After commit, a relay polls unsent rows with FOR UPDATE SKIP LOCKED, enqueues one email task each, and marks them sent. Tasks use acks_late, retry with exponential backoff, and are idempotent by outbox id, so a retry never sends twice. Failures after N tries go to a dead-letter table for review. That also fits the domain_events table the repo already plans for its ETL work.

トランザクショナル・アウトボックス。抽選のトランザクション内で、当選者ごとに outbox 行（種類、宛先、内容）を挿入する。コミット後、中継プロセスが FOR UPDATE SKIP LOCKED で未送信の行を取り出し、それぞれメールタスクをキューに入れて送信済みにする。タスクは acks_late で、指数バックオフで再試行し、outbox の id で冪等にするので再試行でも二重送信しない。N 回失敗したものはデッドレターのテーブルに入れて確認する。これはリポジトリが ETL 用にすでに計画している domain_events テーブルとも合う。
