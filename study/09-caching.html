Topic 09

Caching with RedisRedis によるキャッシュ

Read-heavy pages served from Redis, and the two hard problems: keeping the cache fresh, and surviving when Redis is down.

読み取りの多いページを Redis から返す仕組みと、2つの難題：キャッシュを新しく保つことと、Redis が落ちたときに生き残ること。

TL;DRSay this in 30 seconds30秒で言えること

  • Cache-aside: read Redis; on a miss, build the page from Postgres and store it with a 5-minute TTL.キャッシュアサイド：Redis を読み、なければ Postgres からページを作り、5分の TTL 付きで保存する。
  • Values are Pydantic models dumped to JSON-safe dicts and packed with msgpack (smaller and faster than JSON).値は Pydantic モデルを JSON 互換の dict にして msgpack で詰める（JSON より小さく速い）。
  • Writes delete the affected keys after committing. The TTL is the safety net for anything missed.書き込みはコミット後に影響するキーを削除する。漏れたものは TTL が安全網になる。
  • The code is split into a read side (CacheService) and an invalidation side (CacheInvalidation) to avoid circular imports.循環 import を避けるため、読み取り側（CacheService）と削除側（CacheInvalidation）に分けている。
  • Weak spot: a Redis outage currently turns into 500s (bug #11).弱点：現状では Redis の障害が 500 エラーになる（バグ #11）。

Caching patternsキャッシュのパターン

PatternパターンHow仕組みNote備考
Cache-aside (used here)キャッシュアサイド（本プロジェクト）App reads cache, fills it on a miss, deletes on writeアプリがキャッシュを読み、なければ埋め、書き込み時に削除Simple; the cache can be briefly stale単純。一時的に古くなることがある
Write-throughライトスルーEvery write updates DB and cache together書き込みのたびに DB とキャッシュを両方更新Fresher; every write pays for the cache新しさは保てるが、書き込みごとにキャッシュのコスト
Write-behindライトビハインドWrite to cache, flush to DB laterキャッシュに書き、後で DB に反映Fast; risks losing data速いがデータ喪失の危険

Delete, don't update更新ではなく削除

On a write, deleting the key is safer than writing the new value into it. Two concurrent updates can write their cache values in the wrong order, but two deletes can't conflict. The next read rebuilds from the DB, which is the source of truth.

書き込み時は、新しい値をキャッシュに書くよりキーを削除する方が安全。同時に2つ更新すると、キャッシュへの書き込み順が逆になることがあるが、削除同士は衝突しない。次の読み取りで、正である DB から作り直す。

Three classic cache failuresキャッシュの3つの典型的な障害

  • Stampede: a hot key expires and 1,000 requests all miss and hit the DB at once. Fix: a lock or single-flight so only one rebuilds, or refresh early.スタンピード：人気のキーが切れ、1000件のリクエストが同時に外れて DB に殺到する。対策：ロックやシングルフライトで1つだけ作り直す、または期限前に更新する。
  • Stale write-back: request A misses and reads old data; a writer commits and deletes the key; A then stores the old data. The TTL bounds how long it lasts.古い値の書き戻し：リクエスト A が外れて古いデータを読む。書き込み側がコミットしてキーを削除する。その後 A が古いデータを保存する。TTL がその期間の上限になる。
  • Penetration: requests for ids that don't exist always miss. Fix: cache the "not found" briefly.キャッシュ貫通：存在しない id へのリクエストは常に外れる。対策：「見つからない」も短時間キャッシュする。

1. A cache-aside read1. キャッシュアサイドの読み取り

def get_cached_concert_detail(db: Session, id: uuid.UUID) -> ConcertDetailRead | None:
    cache_key = concert_detail_key(id)
    cached = redis_client.get(cache_key)
    if cached:
        return ConcertDetailRead.model_validate(msgpack.unpackb(cached, raw=False))
    result = ConcertService.get_concert_detail_public(db, id)
    if not result:
        return None
    redis_client.setex(cache_key, TTL_SECONDS, msgpack.packb(result.model_dump(mode="json")))
    return result

The cached value goes through the same Pydantic schema on the way out, so a cache hit and a DB read return exactly the same shape.

キャッシュの値は取り出すときにも同じ Pydantic スキーマを通るので、キャッシュから返しても DB から返しても形はまったく同じ。

2. Keys and invalidation2. キーと削除

TTL_SECONDS = 60 * 5
PRODUCTS_LIST_KEY = "products:list"

def concert_detail_key(id): return f"concerts:{id}:detail"

# Every write that affects a concert detail knows its concert_id, so this deletes one key.
def delete_cached_concert_detail(id): redis_client.delete(concert_detail_key(id))

def _delete_matching(pattern):
    # keys() is an O(N) scan; fine at this key count, use SCAN if that grows.
    keys = redis_client.keys(pattern)
    if keys: redis_client.delete(*keys)

·

Always after the commit. Deleting before the commit opens a window where another request refills the cache with the old data.

必ずコミットの後。コミット前に削除すると、その間に別のリクエストが古いデータでキャッシュを埋め直す隙間ができる。

4. Why two classes4. なぜクラスが2つあるのか

CacheService (reads) calls services to fill the cache. Services (checkout, draw) need to invalidate. If services imported CacheService, the imports would loop. So CacheInvalidation depends only on Redis, services import that, and CacheService inherits from it ().

CacheService（読み取り）はキャッシュを埋めるためにサービスを呼ぶ。一方でサービス（購入、抽選）は削除する必要がある。サービスが CacheService を import すると import が循環する。そこで CacheInvalidation は Redis にだけ依存させ、サービスはそれを import し、CacheService はそれを継承する（）。

WHYWhy this design, and what it costsこの設計を選んだ理由とそのコスト

  • Cache whole page payloads: the store and events pages join many tables. Caching the finished payload turns many queries into one Redis GET.ページ全体をキャッシュ：ストアや公演のページは多くのテーブルを JOIN する。完成した結果をキャッシュすれば、多数のクエリが Redis の GET 1回になる。
  • Short TTL plus explicit deletes: explicit deletes keep data fresh after known writes; the 5-minute TTL catches anything a developer forgot to invalidate.短い TTL と明示的な削除：既知の書き込み後は明示的な削除で新しさを保ち、削除し忘れたものは5分の TTL で拾う。
  • Stock numbers can be stale on screen: that's acceptable, because checkout re-reads stock under a row lock. The cache is for display, never for decisions.画面上の在庫数は古くてもよい：購入時は行ロック付きで在庫を読み直すので許容できる。キャッシュは表示用で、判断には使わない。

WEAK SPOTSKnown gaps you should own自分から説明すべき既知の問題

bugs.md #11

A cache outage becomes a site outage. redis_client.get() raises before the DB fallback runs, so pages 500 even though Postgres could answer. Invalidation after a commit raises too, so a successful write returns 500. And the client has no socket timeout, so a dropped connection hangs a thread. Plan: catch RedisError on reads and fall back to the DB, make invalidation best-effort, and set short timeouts ().

キャッシュの障害がサイト全体の障害になる。redis_client.get() が DB へのフォールバックより先に例外を出すので、Postgres が答えられるのにページが 500 になる。コミット後の削除も例外を出すので、成功した書き込みが 500 を返す。さらにクライアントにソケットのタイムアウトがないため、切れた接続でスレッドが止まる。計画：読み取りで RedisError を捕まえて DB に切り替え、削除は失敗しても続行し、短いタイムアウトを設定する（）。

Also worth mentioningその他言及すべき点

KEYS pattern blocks Redis while it scans every key; SCAN or a Redis set per namespace would be safer at scale. There's no stampede protection on hot pages. Cache, rate limiter and Celery broker share one Redis, so one outage hits all three.

KEYS pattern は全キーを走査する間 Redis をブロックする。大規模なら SCAN か名前空間ごとの Redis のセットが安全。人気ページのスタンピード対策がない。キャッシュ・レート制限・Celery ブローカーが1つの Redis を共有しているので、1回の障害で3つとも影響を受ける。

QUESTIONSPractice questions練習問題

BASICWhat do you cache, and why?何をキャッシュしていますか？なぜ？

Public, read-heavy pages that join many tables: the product list and store page, the events page, idol and group pages, and detail pages. They change rarely compared with how often they're read. Personal data like carts and orders is not cached.

多くのテーブルを JOIN する、公開の読み取りが多いページ：商品一覧とストアページ、公演ページ、アイドルとグループのページ、詳細ページ。読まれる頻度に比べて変更は少ない。カートや注文のような個人のデータはキャッシュしない。

BASICHow do you keep the cache in sync with the database?キャッシュと DB をどう同期させていますか？

After a write commits, the code deletes the keys that write affects, and the next read rebuilds from Postgres. Every key also has a 5-minute TTL, so even a forgotten invalidation heals itself. Anything that must be exact, like stock at checkout, is read from the DB under a lock, never from the cache.

書き込みがコミットされたら、その書き込みが影響するキーを削除し、次の読み取りで Postgres から作り直す。すべてのキーには5分の TTL もあるので、削除し忘れても自然に直る。購入時の在庫のように正確さが必要なものは、キャッシュではなくロック付きで DB から読む。

MIDCan a reader put stale data back into the cache after you invalidated it?削除した後に、読み取り側が古いデータをキャッシュに戻すことはありますか？

Yes. Reader A misses and queries the DB. Before A writes to Redis, a writer commits and deletes the key. Then A stores its old result. Cache-aside can't fully prevent this; the TTL limits it to 5 minutes. For stricter needs: a short delayed second delete, a version number in the key, or a lock around rebuilds.

ある。読み取り A がキャッシュに外れて DB を検索する。A が Redis に書く前に、書き込み側がコミットしてキーを削除する。その後 A が古い結果を保存する。キャッシュアサイドでは完全には防げず、TTL で5分に制限している。より厳密にするなら、少し遅らせた2回目の削除、キーにバージョン番号を入れる、作り直しをロックで囲む、などの方法がある。

MIDWhy msgpack instead of JSON?JSON ではなく msgpack を使うのはなぜ？

It's a binary format, so payloads are smaller and faster to encode and decode, which matters for large page payloads read many times a second. The values are still validated through Pydantic on the way out, so the format is an internal detail.

バイナリ形式なので、データが小さく、エンコードとデコードも速い。1秒に何度も読まれる大きなページには重要。取り出すときは Pydantic で検証するので、形式は内部の詳細にすぎない。

SENIORRedis goes down during a ticket sale. What happens, and what should happen?チケット販売中に Redis が落ちました。何が起き、何が起きるべきですか？

Today: cached reads 500, successful checkouts return 500 after committing because invalidation raises, confirmation emails aren't queued, and a fan might retry with a new idempotency key and pay twice. The rate limiter fails open. What should happen: reads catch RedisError and go to Postgres; invalidation and enqueueing after commit are best-effort and logged; the Redis client has short socket timeouts; and the client reuses its idempotency key on retry. The DB is the source of truth, so the cache should only ever make things faster, never make them fail.

現状：キャッシュの読み取りは 500 になり、成功した購入もコミット後の削除で例外が出て 500 を返す。確認メールはキューに入らず、ファンが新しい冪等キーで再試行して二重に支払うおそれがある。レート制限は素通りする。あるべき姿：読み取りは RedisError を捕まえて Postgres に行く。コミット後の削除とキュー投入は失敗しても続行してログに残す。Redis クライアントに短いソケットのタイムアウトを設定する。クライアントは再試行で同じ冪等キーを使う。正は DB なので、キャッシュは速くするためだけのもので、失敗の原因になってはいけない。
