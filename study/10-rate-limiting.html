Topic 10

Rate limitingレート制限

A fixed-window limiter in Redis, applied per route, keyed by user or IP, and the IP-spoofing hole it still has.

Redis の固定ウィンドウ方式のレート制限。ルートごとに、ユーザーか IP をキーにしてかける。まだ残っている IP 偽装の穴も含めて。

TL;DRSay this in 30 seconds30秒で言えること

  • A dependency factory: Depends(rate_limit(10, 60, ip_key)) means 10 requests per 60 seconds.依存関係のファクトリー：Depends(rate_limit(10, 60, ip_key)) は60秒あたり10リクエスト。
  • Fixed window counter in Redis: SET key 0 EX window NX then INCR, in one MULTI transaction.Redis の固定ウィンドウカウンター：SET key 0 EX window NX と INCR を1つの MULTI トランザクションで。
  • Keys include the route template, so each endpoint has its own budget, and all ids on one route share it.キーにルートのテンプレートを含めるので、エンドポイントごとに枠が分かれ、同じルートの全 id は枠を共有する。
  • Limits are tiered by risk: login 10/min per IP, checkout 3/min per user, public reads 10–30/min.制限はリスクに応じて段階的：ログインは IP ごとに毎分10、購入はユーザーごとに毎分3、公開の読み取りは毎分10〜30。
  • If Redis fails, the limiter fails open (lets requests through).Redis が落ちると、レート制限は素通りする（リクエストを通す）。

Why atomicity mattersなぜアトミック性が重要か

The naive version is INCR then EXPIRE. If the process dies between them, the key has no expiry and that client is blocked forever. Doing both in one MULTI removes the gap. A transaction is enough because neither command needs the other's result; logic that branches on a value read mid-way needs a Lua script.

素朴な実装は INCR の後に EXPIRE。その間でプロセスが落ちるとキーに期限がなく、そのクライアントは永遠にブロックされる。両方を1つの MULTI で行えば隙間がなくなる。どちらのコマンドも相手の結果を必要としないのでトランザクションで十分。途中で読んだ値によって分岐するロジックなら Lua スクリプトが必要。

1. The limiter1. レート制限の本体

def rate_limit(limit: int, window: int, key_func) -> Callable[[Request], None]:
    def limiter(request: Request) -> None:
        try:
            key = key_func(request)
            pipe = redis_client.pipeline(transaction=True)
            pipe.set(key, 0, ex=window, nx=True)   # create with TTL only if missing
            pipe.incr(key)
            _, count = pipe.execute()
            if int(count) > limit:
                raise HTTPException(status_code=429, detail=f"Too many requests. Please try again after {ttl} seconds.")
        except redis.RedisError:
            print("Rate limiter Internal Error")    # fail open
    return limiter

2. The keys2. キー

def _route_key(request):
    # Use the route template (e.g. "/order/single_placed_order/{order_id}"), so every id shares one budget.
    route = request.scope.get("route")
    return route.path if route is not None else request.url.path

def ip_key(request):   return f"rate:ip:{_route_key(request)}:{request.client.host}"
def user_key(request): return f"rate:user:{_route_key(request)}:{request.state.user.id}"
def user_or_ip_key(request): ...  # user if logged in, else IP

Using the template, not the real path, matters: otherwise /orders/1, /orders/2… would each get a fresh budget, and a scraper walking ids would never be limited.

実際のパスではなくテンプレートを使うことが重要。そうしないと /orders/1、/orders/2… がそれぞれ新しい枠を持ち、id を順に辿るスクレイパーが制限されない。

WHYWhy this design, and what it costsこの設計を選んだ理由とそのコスト

  • Redis, not in-process memory: counts must be shared across every web instance and survive restarts.プロセス内メモリではなく Redis：カウントはすべての Web インスタンスで共有し、再起動後も残る必要がある。
  • Fixed window: one key and two commands per request. The 2× burst at a window edge is acceptable for these limits.固定ウィンドウ：リクエストごとにキー1つ、コマンド2つ。ウィンドウ境界での2倍のバーストは、この程度の制限なら許容できる。
  • Fail open: a Redis outage shouldn't take down login and checkout. The cost: during an outage there's no brute-force protection.障害時は素通り：Redis の障害でログインや購入まで止めるべきではない。コスト：障害中は総当たり攻撃への防御がない。

WEAK SPOTSKnown gaps you should own自分から説明すべき既知の問題

bugs.md #7

IP limits can be bypassed. Behind Render's proxy, ProxyHeadersMiddleware(trusted_hosts="*") takes the leftmost X-Forwarded-For entry, which the client writes. Sending a different fake IP each time bypasses login limits: 30 wrong-password logins with a rotating header got zero 429s. Fix plan: read the header from the right, skipping exactly N trusted proxy hops, and add a per-account failed-login limit ().

IP の制限を回避できる。Render のプロキシの後ろでは、ProxyHeadersMiddleware(trusted_hosts="*") が X-Forwarded-For の一番左を使うが、そこはクライアントが書ける。毎回違う偽の IP を送ればログインの制限を回避できる：ヘッダーを変えながら30回パスワードを間違えても 429 は0回だった。修正計画：ヘッダーを右から読み、信頼するプロキシの段数 N だけ飛ばす。さらにアカウントごとのログイン失敗回数の制限を追加する（）。

bugs.md #22, #28

user_key reads request.state.user, which only exists if the auth dependency ran first. #28 was exactly this: a route used user_key without get_current_user, the key function raised AttributeError, and the limiter only catches RedisError, so every call returned 500. The ordering dependency is still implicit.

user_key は request.state.user を読むが、これは認証の依存関係が先に動いたときにしか存在しない。#28 がまさにこれ：あるルートが get_current_user なしで user_key を使い、キー関数が AttributeError を出したが、レート制限は RedisError しか捕まえないので、毎回 500 になった。この順序の依存関係は今も暗黙のまま。

QUESTIONSPractice questions練習問題

BASICHow does your rate limiter work?レート制限はどう動きますか？

It's a FastAPI dependency. For each request it builds a key from the route and the user or IP, and in one Redis transaction creates the counter with a TTL if it's missing and increments it. If the count is over the limit it returns 429 with the seconds left. When the window's TTL expires, the counter disappears and the budget resets.

FastAPI の依存関係。リクエストごとにルートとユーザーまたは IP からキーを作り、1つの Redis トランザクションで、なければ TTL 付きでカウンターを作ってから1増やす。制限を超えたら残り秒数付きで 429 を返す。ウィンドウの TTL が切れるとカウンターが消え、枠がリセットされる。

BASICWhy limit login by IP but checkout by user?ログインは IP で、購入はユーザーで制限するのはなぜ？

At login there's no user yet; the attacker is trying to become one, so IP is the only identity available. Checkout needs a logged-in user, and keying by user stops one account from hammering it from many IPs, while not punishing everyone behind a shared IP like a campus network.

ログイン時にはまだユーザーがおらず、攻撃者はユーザーになろうとしているので、使える識別子は IP だけ。購入はログインが必要なので、ユーザーをキーにすれば1つのアカウントが多数の IP から連打するのを防げ、大学のネットワークのように IP を共有する人たちをまとめて罰することもない。

MIDWhat's wrong with a fixed window, and when would you switch?固定ウィンドウの問題点は？いつ切り替えますか？

A client can send the full limit at the end of one window and again at the start of the next, so twice the limit in a moment. For login at 10/min that's fine. For a strict API quota, or protecting a fragile downstream, I'd use a sliding window counter or a token bucket in a Lua script so the check and update stay atomic.

クライアントは1つのウィンドウの終わりと次のウィンドウの始めにそれぞれ上限まで送れるので、一瞬で上限の2倍になる。毎分10回のログインなら問題ない。厳密な API の割り当てや、壊れやすい下流の保護なら、確認と更新をアトミックに保つため、Lua スクリプトでスライディングウィンドウカウンターかトークンバケットを使う。

MIDShould a rate limiter fail open or closed?レート制限は障害時に素通りさせるべきか、止めるべきか？

It depends on what it protects. Here it fails open: a Redis outage shouldn't lock every fan out of login and checkout, and the DB still enforces stock and money rules. For something where abuse is very costly, like an SMS endpoint that costs money per message, I'd fail closed or fall back to a small in-process limit.

何を守るかによる。ここでは素通りさせる：Redis の障害で全ファンがログインや購入をできなくなるべきではなく、在庫やお金のルールは DB が引き続き守る。1通ごとに費用がかかる SMS 送信のように悪用のコストが高いものなら、止めるか、プロセス内の小さな制限に切り替える。

SENIORHow do you find the real client IP behind a proxy?プロキシの後ろで本当のクライアント IP をどう調べますか？

Each proxy appends the address it received the request from to X-Forwarded-For, so the rightmost entries are written by your own infrastructure and the leftmost by the client. Know how many trusted hops N you have, and take the N-th entry from the right. Never trust the leftmost. And since a real attacker can use many IPs, add limits keyed by the target account too, like 5 failed logins per email per 15 minutes.

各プロキシは、自分がリクエストを受け取った相手のアドレスを X-Forwarded-For の末尾に追加する。そのため右側の値は自分のインフラが書き、左側の値はクライアントが書く。信頼できるプロキシの段数 N を把握し、右から N 番目の値を使う。一番左は決して信用しない。さらに本物の攻撃者は多数の IP を使えるので、対象アカウントをキーにした制限も追加する。例えばメールアドレスごとに15分で5回までのログイン失敗。
