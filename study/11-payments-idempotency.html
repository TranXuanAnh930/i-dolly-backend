Topic 11

Payments & idempotency決済と冪等性

A mock gateway for development, PayPal for real money, and how a retried checkout avoids charging twice.

開発用のモック決済、実際のお金用の PayPal、そして再試行した購入で二重に請求しない仕組み。

TL;DRSay this in 30 seconds30秒で言えること

  • Two gateways behind one service: mock (instant success or failure) and PayPal (redirect, approve, then capture).1つのサービスの裏に2つの決済手段：モック（即座に成功か失敗）と PayPal（リダイレクト、承認、その後キャプチャ）。
  • The client sends an idempotency key (UUID) with each checkout. A reused key gets 409, backed by a UNIQUE constraint.クライアントは購入ごとに冪等キー（UUID）を送る。再利用したキーには 409 を返し、UNIQUE 制約で裏付ける。
  • The server recomputes the total (with 10% tax) and rejects any mismatch with what the client sent.サーバーは合計を再計算（消費税10%込み）し、クライアントの金額と一致しなければ拒否する。
  • PayPal finalization is idempotent: it only acts on a pending payment, under a row lock, so the redirect and the webhook can't both apply it.PayPal の確定処理は冪等：行ロックのもとで pending の決済にだけ作用するので、リダイレクトと Webhook の両方が適用することはない。
  • Webhooks are signature-verified with PayPal before anything is trusted.Webhook は何かを信用する前に、PayPal に問い合わせて署名を検証する。

PRIMERThe theory you need必要な理論

Idempotency冪等性

An operation is idempotent if doing it twice has the same effect as doing it once. Networks lose responses: the server charged the card but the client timed out and retries. Without idempotency, that's a double charge. With an idempotency key, the client marks "this is the same attempt", and the server recognizes the retry.

2回行っても1回と同じ結果になる操作を冪等という。ネットワークではレスポンスが失われる：サーバーはカードに請求したが、クライアントはタイムアウトして再試行する。冪等でなければ二重請求になる。冪等キーがあれば、クライアントは「これは同じ試行だ」と示し、サーバーは再試行だと分かる。

Redirect-based payment flowリダイレクト型の決済フロー

1. checkout      → our API creates a PayPal order, saves Payment(status=pending), returns approval URL
2. fan approves  → on PayPal's site
3. capture       → frontend calls our API → we call PayPal "capture" → mark paid
4. webhook       → PayPal also calls us, in case step 3 never happened

Steps 3 and 4 can both arrive, in any order, more than once. Finalization must be safe to run many times.

手順3と4はどちらも、順不同で、複数回届くことがある。確定処理は何回実行しても安全でなければならない。

Never trust the client's priceクライアントの価格は信用しない

The client can send any amount. The server must compute the total from its own data and treat the client's number only as a check that both sides agree.

クライアントはどんな金額でも送れる。サーバーは自分のデータから合計を計算し、クライアントの数字は双方が一致していることの確認にだけ使う。

1. Idempotency key: check + constraint1. 冪等キー：確認と制約

# service pre-check (fast, clear error)
if db.query(Payment).filter(Payment.idempotency_key == payment_data.idempotency_key).first():
    raise DuplicateIdempotencyKeyError()          # 409

# migration: the real guarantee, for two retries racing each other
op.create_unique_constraint('uq_payment_idempotency_key', 'payment', ['idempotency_key'])

· ·

Two retries arriving together both pass the pre-check, but only one INSERT can win the UNIQUE index. The other gets an IntegrityError, which commit_or_raise translates into the same 409.

同時に届いた2つの再試行はどちらも事前確認を通過するが、UNIQUE インデックスで INSERT に成功するのは1つだけ。もう1つは IntegrityError になり、commit_or_raise が同じ 409 に変換する。

2. Server-side total2. サーバー側での合計

# Japan's consumption tax. Prices are stored tax-exclusive; must match the frontend's tax.js.
TAX_RATE = 0.1
def with_tax(amount: float) -> int:
    # Round half up like JS Math.round (Python's round() rounds half to even)
    return int(amount * (1 + TAX_RATE) + 0.5)

total_amount = sum(with_tax(item.total_price) for item in cart_items)
if payment_data.amount != total_amount:
    raise PaymentAmountMismatch("Payment amount does not match cart total!")

·

Yen has no minor unit, so totals are whole integers. The rounding rule is spelled out so the backend and the JavaScript frontend agree to the yen.

円には小数の単位がないので、合計は整数になる。バックエンドと JavaScript のフロントエンドが1円単位で一致するよう、丸め方を明示している。

4. Idempotent PayPal finalization4. 冪等な PayPal の確定処理

payment = db.query(Payment).filter(Payment.pg_order_id == pg_order_id).with_for_update().first()
if not payment or payment.status != PaymentStatus.pending or (user_id and payment.user_id != user_id):
    return None          # already finalized, or not yours: do nothing
...
paypal_payment = capture_order(pg_order_id)
if paypal_payment["status"] == "COMPLETED":
    payment.status = PaymentStatus.success
    ...
commit_or_raise(db)

The row lock serializes the redirect call and the webhook. Whichever comes second sees success and does nothing. The state machine is the idempotency.

行ロックでリダイレクト経由の呼び出しと Webhook を直列化する。後から来た方は success を見て何もしない。状態遷移そのものが冪等性になっている。

WHYWhy this design, and what it costsこの設計を選んだ理由とそのコスト

  • Client-generated key: only the client knows two requests are the same attempt. The server can't tell a retry from a second purchase.クライアントが作るキー：2つのリクエストが同じ試行だと知っているのはクライアントだけ。サーバーには再試行と2回目の購入の区別がつかない。
  • 409 instead of replaying the first response: simpler, but the client must look up the result itself (order history, payment status) after a 409.最初のレスポンスを返し直すのではなく 409：単純だが、409 の後はクライアントが自分で結果を確認する必要がある（注文履歴、決済状況）。
  • A mock gateway on purpose: the whole checkout, locking and stock logic can be developed and tested without a sandbox account or network.意図的なモック決済：サンドボックスのアカウントやネットワークなしで、購入・ロック・在庫のロジック全体を開発・テストできる。

WEAK SPOTSKnown gaps you should own自分から説明すべき既知の問題

bugs.md #8

PayPal calls inside the transaction. capture_order runs while holding FOR UPDATE on the payment, ticket type and products. If PayPal captures but our commit fails or the response times out, the fan is charged and our DB still says pending. Then the webhook tries to capture again, PayPal answers "already captured", and it never resolves. Fix: the webhook should apply the event's state, not re-capture; and the capture call should move outside the locked transaction. create_order in checkout has the same shape.

トランザクション内での PayPal 呼び出し。capture_order は payment・ticket type・products に FOR UPDATE をかけたまま実行される。PayPal 側でキャプチャが成功したのに、こちらのコミットが失敗したりレスポンスがタイムアウトしたりすると、ファンは請求済みなのに DB は pending のまま。すると Webhook が再度キャプチャを試み、PayPal は「キャプチャ済み」と返し、いつまでも解決しない。対策：Webhook は再キャプチャせずイベントの状態を反映する。キャプチャの呼び出しはロック中のトランザクションの外に出す。購入時の create_order も同じ形。

bugs.md #12, #26, #27

Pending forever. If a fan never approves on PayPal, the order or ticket stays pending with no expiry. A pending direct-sale ticket blocks the fan from buying again (#12), a pending order can be marked shipped (#26), and stale orders pile up (#27). One fix covers all three: a deadline on pending payments and a sweep job that cancels them.

永遠に pending。ファンが PayPal で承認しなければ、注文やチケットは期限なしで pending のまま。pending の直接販売チケットがあるとファンは再購入できず（#12）、pending の注文が発送済みにできてしまい（#26）、古い注文がたまっていく（#27）。1つの修正で3つとも解決できる：pending の決済に期限を設け、それを取り消す一括処理のジョブを作る。

QUESTIONSPractice questions練習問題

BASICHow do you stop a double charge when a fan double-clicks "Pay"?ファンが「支払う」をダブルクリックしたとき、二重請求をどう防ぎますか？

The frontend generates one idempotency key per checkout attempt and sends it with both clicks. The first request stores a payment with that key. The second finds it and gets 409, or, if both arrive at once, loses on the UNIQUE constraint and gets the same 409. Rate limiting (3 checkouts per minute) is an extra guard.

フロントエンドは購入の試行ごとに冪等キーを1つ作り、2回のクリックの両方でそれを送る。最初のリクエストがそのキーで決済を保存する。2回目はそれを見つけて 409 になる。同時に届いた場合も UNIQUE 制約で負けて同じ 409 になる。レート制限（毎分3回の購入）も追加の防御になる。

BASICWhy does the client send the amount at all, if the server computes it?サーバーが計算するのに、なぜクライアントも金額を送るのですか？

As a consistency check. The fan saw a price on screen; if the server's total differs (a price changed, a tax bug), it's better to refuse than to charge a different amount than the fan agreed to. The server's number is what's charged; the client's is only compared.

一致の確認のため。ファンは画面で価格を見ている。サーバーの合計が違う場合（価格の変更、税のバグ）、ファンが同意したのと違う金額を請求するより拒否する方がよい。請求するのはサーバーの金額で、クライアントの金額は比較に使うだけ。

MIDWhy do you need a webhook if the frontend already calls capture?フロントエンドがキャプチャを呼ぶのに、なぜ Webhook が必要ですか？

The fan might close the tab after approving, lose network, or the capture call might time out. The webhook is PayPal telling us directly, with retries, so we eventually learn the outcome. Because both paths run the same finalization, which only acts on pending under a lock, receiving both is harmless.

ファンが承認後にタブを閉じたり、通信が切れたり、キャプチャの呼び出しがタイムアウトしたりすることがある。Webhook は PayPal が再試行付きで直接知らせてくれるものなので、最終的に結果を知ることができる。どちらの経路も同じ確定処理を実行し、それはロックのもとで pending にだけ作用するので、両方届いても問題ない。

MIDHow do you know a webhook really came from PayPal?Webhook が本当に PayPal から来たとどう分かりますか？

The endpoint is public, so anyone could post a fake "payment completed". We take PayPal's transmission headers and the raw body and call PayPal's verify-webhook-signature API; only a SUCCESS answer is accepted, anything else is a 400. We read the raw bytes because re-serialized JSON might not match what was signed.

エンドポイントは公開されているので、誰でも偽の「支払い完了」を送れる。PayPal の送信ヘッダーと生の本文を使って PayPal の verify-webhook-signature API を呼び、SUCCESS の答えだけを受け入れ、それ以外は 400 にする。JSON を再シリアライズすると署名された内容と一致しないことがあるので、生のバイト列を読む。

SENIORPayPal captured the money, but your commit failed. Now what?PayPal はお金をキャプチャしたのに、コミットが失敗しました。どうしますか？

That's bug #8, and there's no distributed transaction to save us. The fix is to design for reconciliation: (1) call capture outside any locked transaction, then update our DB in a short transaction keyed by the PayPal order id; (2) make the webhook apply PayPal's reported state (CAPTURED) instead of calling capture again; (3) run a periodic reconciliation job comparing our pending payments with PayPal's order status; (4) if stock is gone by the time the money arrives, refund automatically.

それがバグ #8 で、助けてくれる分散トランザクションはない。対策は突き合わせを前提に設計すること：(1) キャプチャはロック中のトランザクションの外で呼び、PayPal の注文 id をキーにした短いトランザクションで DB を更新する。(2) Webhook は再キャプチャせず、PayPal が伝える状態（CAPTURED）を反映する。(3) こちらの pending の決済と PayPal の注文状態を比べる定期的な突き合わせジョブを動かす。(4) お金が届いた時点で在庫がなければ自動で返金する。

SENIORHow would you improve your idempotency design?冪等性の設計をどう改善しますか？

Store the key with a hash of the request body and the response. On a retry with the same key and body, return the stored response instead of 409, so the client doesn't need to know it was a retry. The same key with a different body is a client bug, so 422. Keep keys for a limited time (for example 24 hours) and scope them per user, so one user's key can't collide with another's.

キーと一緒にリクエスト本文のハッシュとレスポンスを保存する。同じキー・同じ本文の再試行には 409 ではなく保存したレスポンスを返せば、クライアントは再試行だったことを気にしなくてよい。同じキーで本文が違うのはクライアントのバグなので 422。キーは一定期間（例えば24時間）だけ保存し、ユーザーごとに区切って、他のユーザーのキーと衝突しないようにする。
