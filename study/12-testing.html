Topic 12

Testing strategyテスト戦略

923 tests in two suites, a throwaway Postgres per run, and the guard rails added after tests once wrote into the dev database.

2つのスイートに923個のテスト、実行ごとに作り直す Postgres、そしてテストが開発 DB に書き込んでしまった後に追加した安全装置。

TL;DRSay this in 30 seconds30秒で言えること

  • Unit (531 tests): services with a mocked Session and fake Redis. Fast, no Postgres.単体（531個）：モックの Session と偽の Redis でサービスをテスト。速く、Postgres 不要。
  • Integration (392 tests): real HTTP through TestClient, real Postgres with real triggers, migrated from empty each run.統合（392個）：TestClient で本物の HTTP、本物のトリガー付きの本物の Postgres。毎回空から マイグレーションする。
  • Race tests use real threads and a barrier (topic 06). Permission tests hit every role (topic 05).競合テストは実スレッドと Barrier を使う（トピック06）。権限テストは全ロールで確認する（トピック05）。
  • Together: 94.6% line coverage. CI runs lint, migrations and both suites on every push, and deploys only if they pass.合わせて行カバレッジ94.6%。CI はプッシュごとに lint・マイグレーション・両スイートを実行し、通ったときだけデプロイする。

Coverage is a floor, not a goalカバレッジは下限であって目標ではない

Line coverage says a line ran, not that its result was checked. A test with no assertions can reach 100%. Branch coverage is stricter, and mutation testing (change the code, see if a test fails) is stricter still. The best signal that a test is useful: it fails when you break the thing it's about.

行カバレッジは行が実行されたことを示すだけで、結果が確認されたことは示さない。アサーションのないテストでも100%になりうる。分岐カバレッジはより厳しく、ミューテーションテスト（コードを変えてテストが失敗するか見る）はさらに厳しい。テストが役に立つかの一番の目安：対象を壊したときに失敗すること。

3. The guard added after a real incident3. 実際の事故の後に追加した安全装置

def _assert_app_session_targets_test_database() -> None:
    from app.db.session import engine
    bound = engine.url.database
    if not (bound and bound.endswith("_test")):
        raise RuntimeError(f"app.db.session is bound to {bound!r}, which is not a _test database ...")

If import order ever broke the redirect, the race harness would seed and mutate the real database. It happened once: test products, racer users and their orders appeared in the dev DB. Now the suite refuses to start instead.

import の順番が崩れて切り替えが効かないと、競合テストのハーネスが本物の DB にデータを作って変更してしまう。実際に一度起きた：テスト用の商品、競合テストのユーザーとその注文が開発 DB に現れた。今はテストスイートが起動を拒否する。

WHYWhy this design, and what it costsこの設計を選んだ理由とそのコスト

  • Real Postgres, not SQLite: the rules that matter most here (triggers, FOR UPDATE, enums, generated columns) don't exist in SQLite. Testing on it would prove nothing about them.SQLite ではなく本物の Postgres：ここで最も重要なルール（トリガー、FOR UPDATE、enum、生成列）は SQLite に存在しない。SQLite でテストしても何も証明できない。
  • Two suites: unit tests run anywhere in seconds; integration tests are slower but catch what mocks can't. Neither reaches 94.6% alone (unit alone is 66%).2つのスイート：単体テストはどこでも数秒で動く。統合テストは遅いがモックでは捕まえられないものを捕まえる。どちらも単独では94.6%にならない（単体だけなら66%）。
  • fakeredis everywhere: no Redis needed to run tests, at the cost of never testing real Redis behavior like timeouts or outages.どこでも fakeredis：テストの実行に Redis が不要。代わりに、タイムアウトや障害のような本物の Redis の挙動はテストされない。

QUESTIONSPractice questions練習問題

BASICHow do you test your backend?バックエンドをどうテストしていますか？

Two suites. Unit tests call services with a mocked session to cover business-rule branches quickly. Integration tests go through real HTTP into a real Postgres that's rebuilt from migrations each run, so triggers, constraints and locks are exercised. On top of that there are race tests with real threads and a permission matrix per role. CI runs everything on every push; about 923 tests, 94.6% line coverage.

2つのスイート。単体テストはモックのセッションでサービスを呼び、業務ルールの分岐を素早くカバーする。統合テストは本物の HTTP から、毎回マイグレーションで作り直す本物の Postgres まで通すので、トリガー・制約・ロックも動く。さらに実スレッドによる競合テストと、ロールごとの権限テストがある。CI はプッシュごとにすべて実行する。約923個のテストで行カバレッジ94.6%。

BASICWhy not just use SQLite for tests? It's faster.テストに SQLite を使わないのはなぜ？速いのに。

The most important behavior is Postgres-specific: PL/pgSQL triggers, SELECT … FOR UPDATE, enum types, generated columns, gen_random_uuid(). SQLite has none of these, so tests would pass while production breaks. Test against the database you run.

最も重要な挙動が Postgres 固有だから：PL/pgSQL のトリガー、SELECT … FOR UPDATE、enum 型、生成列、gen_random_uuid()。SQLite にはどれもないので、テストは通るのに本番で壊れる。本番で使う DB に対してテストする。

MIDTell me about a test-infrastructure bug you fixed.直したテスト基盤のバグについて話してください。

The suite redirects DATABASE_URL to a _test database, but the app's engine is created once at first import. At one point the redirect didn't take effect for the engine the race harness writes through, and the concurrency tests seeded products, users and orders into the dev DB. I added a startup assertion that the engine's database name ends in _test; otherwise the suite refuses to run. Plus an autouse fixture that mocks Celery so unit tests can't send real emails.

スイートは DATABASE_URL を _test の DB に切り替えるが、アプリのエンジンは最初の import 時に1回だけ作られる。ある時、競合テストのハーネスが書き込むエンジンに切り替えが効いておらず、並行性テストが開発 DB に商品・ユーザー・注文を作ってしまった。エンジンの DB 名が _test で終わることを起動時に確認し、そうでなければスイートの実行を拒否するようにした。さらに、単体テストが本物のメールを送らないよう Celery をモックする autouse フィクスチャも入れた。

MIDYou have 94.6% coverage. Is the code well tested?カバレッジは94.6%です。十分にテストされていますか？

Not necessarily. It's line coverage, so a line counts even if only one side of its if ran, or nothing was asserted. The more convincing evidence is specific: the race tests fail if you remove the lock, the shipping tests fail against the old IDOR code. Next steps: turn on branch coverage and add tests for failure modes like Redis being down.

必ずしもそうではない。行カバレッジなので、if の片側しか通っていなくても、何も確認していなくても、その行は数えられる。より説得力があるのは具体的な証拠：ロックを外すと競合テストが失敗する、古い IDOR のコードでは配送先のテストが失敗する。次の一歩は、分岐カバレッジを有効にし、Redis の停止のような障害時のテストを追加すること。

SENIORHow would you make the integration suite faster without losing confidence?信頼性を落とさずに統合テストを速くするには？

(1) Wrap each non-concurrency test in a transaction with a SAVEPOINT and roll back at the end, instead of creating and deleting rows; the race tests keep real commits because they need separate connections. (2) Build the migrated schema once and clone it with CREATE DATABASE … TEMPLATE per worker. (3) Run in parallel with pytest-xdist, one database per worker. (4) Keep a small smoke set on every push and the full suite on merge.

(1) 並行性テスト以外は、行を作って消す代わりに、各テストを SAVEPOINT 付きのトランザクションで囲んで最後にロールバックする。競合テストは別々の接続が必要なので本物のコミットのまま。(2) マイグレーション済みのスキーマを1回だけ作り、ワーカーごとに CREATE DATABASE … TEMPLATE で複製する。(3) pytest-xdist でワーカーごとに1つの DB を使って並列実行する。(4) プッシュごとには小さなスモークテスト、マージ時に全体を実行する。
