PRIMERHow to talk about weaknesses弱点の話し方

"What would you improve?" is a test of judgment, not a trap. A strong answer has four parts: what the problem is, the impact (who gets hurt, how badly), why it exists (a trade-off, or an honest miss), and the fix with its cost. Rank by impact, not by how easy it is to explain. Never claim there are no problems.

「何を改善しますか？」は罠ではなく判断力のテスト。良い答えは4つの要素を持つ：問題が何か、影響（誰がどれだけ困るか）、なぜ存在するか（トレードオフか、正直な見落としか）、そしてコスト付きの修正。説明しやすさではなく影響の大きさで順位を付ける。問題がないとは決して言わない。

BASICWhat's the weakest part of this project?このプロジェクトで一番弱い部分は？

Failure handling between systems. Inside Postgres, things are atomic and well tested. But PayPal calls happen inside locked transactions, and Redis failures after a commit surface as 500s. In both cases a successful operation can look failed, and a fan might pay twice. Both have written fix plans: move external calls out of transactions, make post-commit work best-effort, and reconcile with PayPal.

システム間の失敗の扱い。Postgres の中はアトミックでよくテストされている。しかし PayPal の呼び出しはロック中のトランザクション内で行われ、コミット後の Redis の失敗は 500 として表に出る。どちらの場合も成功した操作が失敗に見え、ファンが二重に支払うおそれがある。両方とも修正計画を書いてある：外部呼び出しをトランザクションの外に出す、コミット後の処理は失敗しても続行する、PayPal と突き合わせる。

(1) #11 Redis fallback: small change, and today a cache blip can take down the site and cause double payments. (2) #7 IP spoofing: a clear security hole with a written plan. (3) #2 product delete: a migration to RESTRICT plus soft delete, to protect order history. #8 is the most serious but needs a proper design and PayPal sandbox testing, so I'd start its design that week rather than rush it.

(1) #11 Redis のフォールバック：変更は小さく、今はキャッシュの一瞬の不調でサイトが落ち、二重支払いも起きうる。(2) #7 IP の偽装：明確なセキュリティの穴で、計画も書いてある。(3) #2 商品の削除：注文履歴を守るため、RESTRICT と論理削除のマイグレーション。#8 は最も深刻だが、きちんとした設計と PayPal サンドボックスでのテストが必要なので、急がずにその週は設計から始める。

MIDTell me about a security bug you found.見つけたセキュリティバグについて話してください。

Image upload took the file extension from the client's filename. Someone could upload an HTML file with an image content type, and the API would serve it as HTML from its own origin: stored XSS. The fix derives the extension from a whitelist of allowed content types, so the file on disk can only ever be an image type. The broader rule: never let client input decide how your server serves a file.

画像のアップロードで、拡張子をクライアントのファイル名から取っていた。画像のコンテンツタイプで HTML ファイルをアップロードすると、API が自分のオリジンからそれを HTML として配信してしまう：保存型 XSS。修正では許可したコンテンツタイプの一覧から拡張子を決めるので、ディスク上のファイルは必ず画像の種類になる。より広い原則：サーバーがファイルをどう配信するかをクライアントの入力に決めさせない。

SENIORHow do you decide what to fix and what to leave?何を直し、何を残すかをどう決めますか？

Impact times likelihood, against cost. Money and security first, even if rare. Then things that make correct operations look failed, because they cause user retries and support load. Group bugs by root cause so one fix closes several (#12, #26, #27). Things on unused paths (#14) are documented and parked. Everything goes into one tracked backlog with severity, so the decision is visible and can be revisited.

影響×発生確率とコストを比べる。まずお金とセキュリティ、まれでも優先する。次に正しい操作が失敗に見えるもの。ユーザーの再試行やサポートの負担につながるから。根本原因ごとにバグをまとめ、1つの修正で複数を片付ける（#12・#26・#27）。使われていない経路のもの（#14）は記録して保留する。すべてを重要度付きの1つのバグ一覧で管理するので、判断が見えるし見直せる。
