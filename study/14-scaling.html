Topic 14

Scaling & system designスケーリングとシステム設計

The follow-up every portfolio project gets: "What if 100× more fans showed up?" Where i-dolly would break first, and what you'd change.

どのポートフォリオにも来る追加質問：「ファンが100倍になったら？」i-dolly がどこから壊れるか、何を変えるか。

TL;DRSay this in 30 seconds30秒で言えること

  • Today: one web instance (Render), one Celery worker, Supabase Postgres, one Redis. A 10-connection DB pool.現状：Web インスタンス1つ（Render）、Celery ワーカー1つ、Supabase の Postgres、Redis 1つ。DB 接続プールは10本。
  • The web tier is stateless (JWT, state in Postgres and Redis), so adding instances is easy. The database is the real limit.Web 層はステートレス（JWT、状態は Postgres と Redis）なのでインスタンスの追加は簡単。本当の制約はデータベース。
  • The hardest load is a hot row: everyone buying the same tier locks the same row. The lottery exists to avoid that.最も難しい負荷はホットな行：全員が同じ枠を買うと同じ行をロックする。抽選はそれを避けるためにある。
  • Scale in order: measure → connection pooling → read replicas/cache → queue the spikes → split only if needed.順番にスケールする：計測 → 接続プーリング → リードレプリカ/キャッシュ → 急増をキューで吸収 → 必要なときだけ分割。

PRIMERThe theory you need必要な理論

How to answer a scaling questionスケーリングの質問への答え方

  1. Clarify the numbers: users, requests per second at peak, read/write ratio, data size.数字を確認：ユーザー数、ピーク時の秒間リクエスト数、読み書きの比率、データ量。
  2. Find the bottleneck: which resource runs out first (DB connections, CPU, a hot row)?ボトルネックを探す：最初に足りなくなる資源はどれか（DB 接続、CPU、ホットな行）？
  3. Fix that one thing, then find the next. Don't redesign everything.その1つを直し、次を探す。すべてを作り直さない。
  4. Name the trade-off of each change: consistency, cost, complexity.各変更のトレードオフを言う：一貫性、コスト、複雑さ。

Little's Law for connection pools接続プールとリトルの法則

Connections in use ≈ requests per second × seconds each request holds a connection. With 10 connections and 20 ms per query-heavy request, the ceiling is about 500 requests/s. If a request holds a connection for 2 s (say, waiting on PayPal inside a transaction), the ceiling drops to 5 requests/s. Short transactions matter more than big servers.

使用中の接続数 ≈ 秒間リクエスト数 × 1リクエストが接続を持つ秒数。接続10本で1リクエスト20ミリ秒なら上限は毎秒約500件。トランザクション内で PayPal を待つなどして1リクエストが2秒接続を持つと、上限は毎秒5件に落ちる。大きなサーバーより短いトランザクションの方が重要。

2. What's already scale-friendly2. すでにスケールしやすい点

  • Stateless web tier: auth is JWT; nothing lives in process memory except the pool.ステートレスな Web 層：認証は JWT で、プール以外にプロセスのメモリに残るものはない。
  • Shared rate limits in Redis, so they still work with many instances.共有のレート制限が Redis にあるので、インスタンスが増えても機能する。
  • Cached public pages absorb most reads (topic 09).キャッシュされた公開ページが読み取りの大半を吸収する（トピック09）。
  • Heavy work in a worker: the draw doesn't block web threads (topic 08).重い処理はワーカーで：抽選が Web のスレッドを止めない（トピック08）。
  • Lottery instead of first-come-first-served for hot concerts, which spreads demand over the entry window.人気公演では先着順ではなく抽選にして、需要を応募期間全体に分散する。

WHYWhy not build for scale from day oneなぜ最初から大規模向けに作らないのか

  • A monolith with clear domain folders is faster to change, and the domains (identity, talent, events, marketplace) already mark where services could split later.ドメインごとにフォルダが分かれたモノリスは変更が速く、そのドメイン（identity・talent・events・marketplace）が将来サービスを分割できる境界をすでに示している。
  • The design choices that are hard to change later (UUID keys, row locking, idempotency keys, the lottery model) were made early. The easy-to-add ones (replicas, PgBouncer, more instances) can wait until measurements say so.後から変えにくい設計（UUID キー、行ロック、冪等キー、抽選モデル）は早めに決めた。後から足しやすいもの（レプリカ、PgBouncer、インスタンスの追加）は計測結果が必要と示すまで待てる。

WEAK SPOTSWhat's missing for production scale本番規模に足りないもの

Observability可観測性

No logging module (only print()), no metrics, no tracing, no health endpoint beyond /. At scale you can't fix what you can't see: structured logs with a request id, p95/p99 latency per route, DB pool usage and lock-wait time would come before any architecture change.

logging モジュールを使っておらず（print() だけ）、メトリクスもトレースもなく、/ 以外のヘルスチェックもない。規模が大きくなると、見えないものは直せない：アーキテクチャを変える前に、リクエスト id 付きの構造化ログ、ルートごとの p95/p99 のレイテンシ、DB プールの使用率、ロック待ち時間が必要。

QUESTIONSPractice questions練習問題

BASICCan you run more than one instance of your API?API のインスタンスを複数動かせますか？

Yes. Auth is a JWT, sessions aren't in memory, rate-limit counters and cache are in Redis, and all real state is in Postgres. Two things to handle: migrations should move from container start to a single pre-deploy step, and the total of all pools must stay under Postgres's connection limit.

はい。認証は JWT、セッションはメモリになく、レート制限のカウンターとキャッシュは Redis、実際の状態はすべて Postgres にある。対応すべきことは2つ：マイグレーションをコンテナ起動時から単一のデプロイ前の手順に移すこと、全プールの合計を Postgres の接続上限以下に保つこと。

BASICWhat would you add first if traffic grew 10×?トラフィックが10倍になったら最初に何を追加しますか？

Measurement, then a connection pooler. Logs and metrics tell me what's actually slow. PgBouncer in transaction mode lets many app instances share a small number of real Postgres connections, which is usually the first hard limit on Supabase. Then more web instances, since they're stateless.

計測、次に接続プーラー。ログとメトリクスで何が本当に遅いかが分かる。トランザクションモードの PgBouncer なら、多数のアプリのインスタンスが少数の本物の Postgres 接続を共有でき、Supabase ではたいていそれが最初の厳しい制約になる。その後、ステートレスなので Web のインスタンスを増やす。

MIDWould read replicas help? What's the catch?リードレプリカは役に立ちますか？注意点は？

For public reads like listings and detail pages, yes, though the Redis cache already absorbs most of those. The catch is replication lag: a fan who just bought a ticket and immediately loads "my tickets" from a replica might not see it. So user-specific reads right after a write, and every decision (stock checks, locks) must go to the primary.

一覧や詳細ページのような公開の読み取りには役立つが、それらの大半はすでに Redis のキャッシュが吸収している。注意点はレプリケーションの遅延：チケットを買った直後のファンがレプリカから「マイチケット」を読むと、表示されないことがある。書き込み直後のユーザー固有の読み取りと、すべての判断（在庫確認、ロック）はプライマリに送る必要がある。

MIDWhat does PgBouncer's transaction mode break?PgBouncer のトランザクションモードで壊れるものは？

A server connection is only yours for one transaction, so anything tied to a session breaks: session-level SET, advisory locks held across transactions, LISTEN/NOTIFY, and server-side prepared statements unless the driver disables them. i-dolly's row locks are fine, because they live inside one transaction. Row-Level Security using SET LOCAL would also be fine.

サーバー接続は1トランザクションの間だけ自分のものになるので、セッションに結び付くものが壊れる：セッション単位の SET、トランザクションをまたぐアドバイザリーロック、LISTEN/NOTIFY、ドライバーで無効にしない限りサーバー側のプリペアドステートメント。i-dolly の行ロックは1トランザクション内で完結するので問題ない。SET LOCAL を使う行レベルセキュリティも問題ない。

SENIORDesign a direct ticket sale for 200,000 fans and 10,000 seats opening at 10:00.10時開始、20万人のファンと1万席の直接販売を設計してください。

Keep the stampede away from the database. (1) A virtual waiting room in front: fans get a random queue position and are let in at a rate the backend can handle. (2) Reserve in Redis: an atomic DECR on the tier's remaining count; if it goes below zero, sold out immediately, no DB touched. (3) Winners of the decrement get a short hold (say 10 minutes) written to Postgres with the existing locked checkout, which now sees low contention. (4) Expired holds return seats with a sweep job. (5) Idempotency keys and one-ticket-per-concert rules stay in Postgres as the source of truth. Or, as i-dolly does: run it as a lottery.

殺到をデータベースから遠ざける。(1) 前段に仮想待合室：ファンにランダムな順番を付け、バックエンドが処理できる速さで通す。(2) Redis で確保：枠の残数をアトミックに DECR し、0未満になれば DB に触れずに即座に売り切れ。(3) 減算に成功した人には短い仮押さえ（例えば10分）を与え、既存のロック付き購入処理で Postgres に書く。この時点では競合は少ない。(4) 期限切れの仮押さえは一括処理ジョブで席を戻す。(5) 冪等キーと1公演1枚のルールは、正の情報源として Postgres に残す。あるいは i-dolly のように抽選にする。

SENIORWhen would you split this monolith into services?このモノリスをいつサービスに分割しますか？

When a part needs to scale, deploy or fail independently, not before. The first candidate is ticketing (events: campaigns, draw, checkout), because its load is spiky while the talent catalog is steady. The cost is real: checkout today is one Postgres transaction across tickets, payments and notifications. Splitting it means sagas and an outbox instead. Until the numbers force it, a modular monolith with clear domain boundaries is the better trade.

ある部分を独立してスケール・デプロイ・障害分離する必要が出たとき。それより前ではない。最初の候補はチケット（events：キャンペーン、抽選、購入）で、タレントのカタログは安定しているのに負荷が急増しやすいから。コストは本物：今の購入はチケット・決済・通知にまたがる1つの Postgres トランザクション。分割すると代わりにサーガとアウトボックスが必要になる。数字が強いるまでは、ドメインの境界がはっきりしたモジュラーモノリスの方が良い選択。
